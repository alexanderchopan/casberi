# SwiftUI, UIKit and simulator gotchas — the long form

CLAUDE.md keeps one line per gotcha: the rule and where it bites. This file keeps each entry in full — the build it cost, the measurement, the reasoning — verbatim as it stood in CLAUDE.md.

## Moved from CLAUDE.md (2026-09-14)

Verbatim. CLAUDE.md now carries a one-line index entry for each, pointing here.

- **`booted` is ambiguous with two simulators up** (2026-07-21): a second Claude session boots its own device, and from that moment every `xcrun simctl … booted` (install, launch, screenshot) may resolve to THEIR device — as can computer-use/simulator-MCP taps, which pick the frontmost. The symptom reads as a stale build: your new strings are in the binary, the screen shows the old UI, and the app randomly leaves the foreground (they terminated it). Pin the udid on every call (`xcrun simctl list devices booted` to get it, then `xcrun simctl launch <udid> …` and the simulator tool's own `udid:` argument) the moment a second device appears.
- **Verify the INSTALLED binary, not just the newest one** (2026-07-16): `ls -dt` globs across EVERY `Casberi-*` DerivedData dir, so when a second Claude session is building concurrently it can serve you THEIR app — which silently lacks your probe hooks. The symptom is maddening: `probeArgs:` logs your args correctly, and the hooks just never fire (they're absent from the binary, so `string(forKey:)` finds nothing to match). Three runs were misdiagnosed as rate limits and regressions before this was spotted. Check the bundle you actually installed: `strings "$(xcrun simctl get_app_container booted com.casberi.app app)/Casberi" | grep -c '^myHookKey$'` — 1 means it's really there. Concurrent sessions also share one build DB (`database is locked` → just retry until it clears).
- **A quick action is REGISTERED on the app delegate and DELIVERED to the scene delegate (prd §377, 2026-08-14).** `application(_:performActionFor:completionHandler:)` is never called in a scene-based app — which every SwiftUI `App` is; the action goes to `windowScene(_:performActionFor:)`, and a COLD launch arrives as `UIScene.ConnectionOptions.shortcutItem`. Shipped broken for eleven days and looked healthy, because registering and handling are different delegates. `Shell/QuickActions.swift` owns both doors; the durable flag and the `QuickAction.received` notification are both needed, and neither is reachable by any harness here. **STANDING RULE: for any UIKit hook concerning the SCENE — quick actions, state restoration, cold-launch URL/activity continuation — check which delegate the current lifecycle delivers it to before writing the handler; getting it wrong fails silently, and silent here reads as "the app opened normally".** → docs/prd.md §377
- **A feed ROW never carries a presentation of its own — one screen, one `.sheet` (third time paid for, 2026-07-28).** `FeedScreen` presents through exactly ONE `.sheet(item: $feedSheet)` (`FeedSheetRoute`) because five sibling `.sheet` modifiers on the screen made the first tap silently self-dismiss. The same rule reaches DOWN the tree: a `.sheet` attached to a view INSIDE a `List` row resolves to the same presenting UIViewController, so the row's tap starts the thing sheet and the row's own sheet modifier tears it back down mid-transition — the sheet rises PART WAY and closes again. Symptom, user-reported: "opening fc feed items doesn't work, it opens half way and closes". Cause: the 2026-07-27 social pass moved `ReplyingToRow` and `SocialQuoteCard` — both `Button` + `.sheet(isPresented:)`, correct inside `ThingSheetView`, which is itself a presented sheet — into `PostCard`/`SocialThreadCard`, i.e. into feed rows. Farcaster wore it worst because nearly every cast it lands has a parent or a quote (channel casts, mentions and likes are mostly replies), so nearly every fc row grew the extra sheet. THE RULE: a row is a read with ONE gesture (tap → the thing sheet, ruling 2026-07-16); anything walkable inside it renders as context (`allowsHitTesting(false)`), and the walk lives in the sheet, which routes through its own single presentation (`ThingSheetView.walkingTo`). A component used in BOTH places takes a flag (`SocialQuoteCard.walkable`) rather than presenting unconditionally.
- **Decorative motion during a refresh must be CoreAnimation, not SwiftUI** (2026-07-28, user: "the rain pour always lags on pages"). SwiftUI interpolates `.offset`/`.opacity` per frame on the MAIN actor — and every ingest in this app is `@MainActor` (inserts/deletes on the main context, each re-emitting the feed's `@Query`), so a pull-to-refresh delight animates in exactly the window where the main thread is least able to draw it. It stuttered by construction, every time. `Design/TileRain.swift` now deals `CALayer` tiles with a `CAAnimationGroup` (position + opacity, `beginTime` for the stagger, `.backwards` fill), which the render server drives out of process — smooth while the main thread is blocked solid. Corollary from the same fix: ONE gesture deals ONE shower. `refreshFeed()` bumped `chrome.refreshPulse` a second time a few ms after `.refreshable` already had, re-dealing the in-flight drops over the same identities.
- A SwiftData `#Predicate<Thing> { $0.tags.contains(x) }` (`tags` is a transformable `[String]` attribute) COMPILES clean but crashes at RUNTIME — EXC_BAD_ACCESS/SIGSEGV inside CoreData's `_NSCoreDataStringSearch` mid-SQLite-fetch (found 2026-07-21 scoping `ProjectDetailScreen`'s `@Query` to a project's tag as a perf win; reproduced by opening a project, confirmed via crash report, reverted). Plain string-equality predicates (`$0.source == source`) are fine and already used throughout `Model/IngestSupport.swift` — the crash is specific to `.contains` on an array-typed attribute, which SwiftData can't safely push down to SQL here. Filter tag membership in Swift AFTER an unscoped fetch instead; don't reintroduce a tags-array predicate without verifying against a real on-device fetch first.
- `navigationDestination(item:)` gates on VALUE EQUALITY, and SwiftUI writes its own `nil` back into that binding when the pushed screen dismisses — the catalogue-door mint-stamp saga (user: "I have to click it a few times", 2026-07-22). SUPERSEDED 2026-07-22: `HomeRoute` no longer uses `navigationDestination(item:)` at all. Multiple sibling item bindings anchored to the same `NavigationStack` root turned out not to nest — pushing a bridge setup screen (`bridgePush`) while the Apps door (`push`) was open silently dropped Apps out of the real stack, so the native back chevron on a connect screen (Coinbase, Kalshi, …) landed on the Feed instead of the Apps catalog it was opened from. The fix: ONE ordered array, `HomeRoute.path: [HomeRoute.Node]`, bound to `NavigationStack(path:)` in `MainSurface` and resolved via a single `navigationDestination(for: HomeRoute.Node.self)`. Appending is never gated by value equality, so the old mint-stamp workaround (`HomeRoute.Push`, a struct pairing a door with a mint stamp) is gone too — every `path.append` is a real array mutation SwiftUI has never seen before, and an early push sitting in `path` before the stack mounts renders correctly on the first frame (read directly, not edge-triggered) with no re-landing dance. Corollary: a plain (valueless) `NavigationLink { Destination() }` pushes a frame the bound `path` array doesn't track — appending to `path` while one is on top drops it (the stack resyncs to `path`'s own count). Any screen that might later have something pushed onto it via `HomeRoute` needs its OWN entry pushed through `route.path` (`NavigationLink(value:)` against a `HomeRoute.Node` case), not a plain NavigationLink — see `AppsScreen.swift`'s `catalogTap`. (The product page that was this rule's own example is deleted, prd §641.)
- The Home board (and its `Design/BoardDragDriver.swift` UIKit drag-to-reorder layer) retired 2026-07-20 (prd §131, docs/agent-brief.md rulings 11–12) — the app opens on the All feed now, and the agent's kept-ask chips carry the per-app glance job the board used to. Kept as a lesson, not a live gotcha: the three arbitration problems a custom UIKit recognizer on SwiftUI's UIScrollView ran into (a plain SwiftUI drag gesture can't fix scroll-vs-drag arbitration and leaks state on a cancelled drag; target-action on that recognizer fires only intermittently, so deliver callbacks from the recognizer's own touch handlers; a SwiftUI Button's touch-down recognizer force-fails an exclusive ancestor ~40ms into a hold, so a drag driver needs a failure requirement over everything but the scroll pan) are the same class `Screens/AppsScreen.swift`'s deck-pan catcher solved the same way, if a future custom-gesture-vs-UIScrollView fight comes up again.
- **The first frame walks a deep SwiftUI tree and has overflowed the main stack THREE times (2026-07-10, 07-13, 07-15).** It reads as infinite recursion and is not. Two build settings are load-bearing and must not be removed without ~10 install+cold-launch cycles (`scripts/verify.sh` automates exactly that): `OTHER_LDFLAGS -Wl,-stack_size,0x800000` (8MB main stack) and `ENABLE_DEBUG_DYLIB = NO`. **THE RULE, paid for three times: if it recurs, FLATTEN the composition tree, not more stack** — any new card at an EAGER screen HEAD renders flat; the generic `Widget`/`Row` path (~12 levels/row) is fine deeper in a scroll but too deep to stack at the head. → docs/prd.md
- **A `ModelContext` walked OFF the main actor is a SIGSEGV that reads like the liveness class and is not it (prd §617, 2026-09-05).** `SpotlightIndex.reindexAll` was not `@MainActor`, so `await SpotlightIndex.reindexAll(context: modelContext)` at launch hopped to the cooperative pool and walked the main context from a background thread while the main thread built the feed off it — two `EXC_BAD_ACCESS` reports in one afternoon, inside SwiftData under `Thing.tags.getter`, faulting thread `com.apple.root.user-initiated-qos.cooperative`, main thread in `MainSurface.things.getter`. No delete anywhere, just the wrong thread; timing-dependent, so it survived every launch cycle the pass runs. THE RULE: any `async` function handed the main `ModelContext` is `@MainActor`; read the FAULTING THREAD's queue name in a report before reaching for the liveness corollaries.
- **A root-level `.redacted` (or any root `@State` write) on BACKGROUND is a scene-update watchdog kill (prd §614, 2026-09-05).** Builds 511 and 521 died `0x8BADF00D`; the 10s allowance is WALL CLOCK and a backgrounded app is throttled (measured: 10.279s at **16%** CPU), so a ~1.5s render exceeds it. **THE RULE: the app-switcher cover is `Shell/PrivacyCover.swift`'s opaque `UIWindow` at `.alert + 1` — never a modifier on the shell — and nothing writes root-view `@State` on a scene-phase change.** Mechanical as check D of `scripts/privacy-cover-audit.py`. Unreachable by every harness here. → docs/prd.md §614
- **A BACKGROUND LAUNCH still connects the scene, and building the shell there is the same watchdog (prd §642, 2026-09-07).** Build 534 died `0x8BADF00D` 43s old, never on screen — a `BGAppRefreshTask` had launched the app and the window scene connected anyway. **THE RULE: `BackgroundLaunch` asks the SCENE (`connectedScenes` + `activationState`), NOT `UIApplication.applicationState` in `didFinishLaunchingWithOptions`** — that value is derived from scenes, none connected at that callback, so it reads `.background` on EVERY launch and build 537 shipped a blank Mac window (§642b). Four mount doors, and it NEVER unmounts (tearing down on background is §614 again); anything arriving without a window stays ABOVE the gate. `scripts/background-launch-audit.py`; no machine here can background-launch anything. → docs/prd.md §642 · §642b
- **A ROOM MATERIALISED ITS OWN `@Query` FOUR TIMES PER BODY PASS (prd §646, 2026-09-08).** Build 537 died `0x8BADF00D` process-exit, and it is the one watchdog of this family whose report symbolicates — `FeedScreen.roomBody.getter`, with `SwiftData` → `Encodable.encode(to:)` under it. **Reading a `@Query` array is a FETCH PLUS A PER-MODEL `Codable` SNAPSHOT, and it is not cached between reads.** THE RULE: **bind the room's array ONCE per body pass and answer every derived question from that binding** — never re-read the query for a yes/no, never fetch one to key an ANIMATION, and never read it to build a `.task(id:)` key for a task that will return (`corpusRevision`'s own ruling, owed to every key). Mechanical as `scripts/query-read-audit.py`; its companion report, build 534, is a scene-update watchdog whose stack is one LAYOUT pass and which carries no Casberi frame and no surviving dSYM, so it names no view. → docs/verify.md · prd §646
- **A SHEET DRAG LAYS OUT ITS HOSTING VIEW SYNCHRONOUSLY, ON EVERY OFFSET — so a `List` behind a sheet must draw a BOUNDED number of rows (prd §657, 2026-09-08).** Build 539's `0x8BADF00D`, the fourth of §614's family and the first a finger started; `PersonRoomScreen` drew every row about one person, unbounded, and SwiftUI's per-row index walk makes one update O(rows × sections). `Model/RowWindow.swift` is the bound → docs/verify.md · prd §657
- **A `UserDefaults` WRITE INSIDE A LOCK IS A DEADLOCK WITH EVERY VIEW BODY (prd §721, 2026-09-14).** `UserDefaults.set` posts `didChangeNotification` synchronously on the calling thread, and any app with an `@AppStorage` has SwiftUI's observer on it: `userDefaultsDidChange` → `Update.enqueueAction` → the update lock EVERY BODY HOLDS. So a sweep holding `BridgeHealth.lock` and writing defaults inside it deadlocks against any body reading the same store — all 55 account pages do, through `AccountPageState.of`. Build 570's `0x8BADF00D`, reported as *"touching the app catalog icon in top is inactive and leads to crashing on multiple pages"*: the door was fine, the main thread was dead, so every control on every page was. **THE RULE: nothing inside a lock the main thread can contend may call out to observers — persist through `Model/DefaultsWrite.swift` (one serial queue, keeping the same-key ordering the write was inside the lock FOR).** Mechanical as `scripts/defaults-lock-audit.py`; unreachable by every harness and probe here
- **Chrome pinned INSIDE an `.id()` subtree is destroyed by the very transition it commands (prd §357, 2026-08-11).** A `.safeAreaInset` declared on `FeedScreen` (which carries `.id(filter.source)`) dies on every room change — so `CategoryVenueSwitcher`'s `matchedGeometryEffect` namespace died with it and its documented travel could never once have happened. Nothing LOOKED broken, which is why two passes missed it. **THE RULE: a control that PERSISTS ACROSS a room change mounts on the shell (`MainSurface.roomControls`), never on the screen it sits above** — staying inside the `NavigationStack` and self-gating. Mechanical in `category-fold-selftest.sh`. **Corollary: `.id()` is not free chrome-wise — before adding a `safeAreaInset`, ask whether the screen outlives the interaction the inset drives.** → docs/prd.md §357
- **`.fontWeight()` after `.dsText()` DOES work — measured, not assumed (2026-08-11).** `dsText` applies an explicit `.font(.system(size:weight:))`, so an outer weight modifier looks like a plausible no-op, and two shipped controls (the wallet face rail, `CategoryVenueSwitcher`) depend on that combination for their selection weight. Rendered `ImageRenderer` widths for the same string at 12pt: medium **47.0**, semibold **48.0**, font-then-fontWeight **48.0**. It overrides. Recorded because the plausible-but-wrong version of this ("the inner font wins") would have declared two working controls broken and prompted a pointless refactor of the type ramp — the cheap instrument (a 12-line `swift` script) settled it in one run.
- **An `NLEmbedding` is not safe to call from two threads at once — ONE INFERENCE AT A TIME, process-wide (build 281, 2026-08-07).** Builds 280/281 shipped and crashed with two threads inside `CoreNLP::SentenceEmbedding::fillStringVector` at once; the design ASKS for it on every foreground (the backfill is deliberately off the main actor, the query side never leaves main). Proven: 3/3 dead unlocked, 3/3 survivors over 12,000 inferences locked. **THE RULE: every compute call (`vector(for:)`, `neighbors(for:)`, `distance`) goes through `EmbeddingIndex.serialized { }` — ONE gate for EVERY model, not one per instance** (both stacks share `fillWordVectors`, so per-object locking leaves the cross-object case open). **A SERIAL QUEUE, not an `NSLock`** — a mutex is not fair and the first cut traded the crash for a 2.5s main-thread stall (NSLock p95 280–347ms, max 2573ms; serial queue max 15ms). Mechanical in `ondevice-selftest.sh`; invisible to every check here, since the simulator ships no on-device model. It also reads exactly like the SwiftData liveness class and is not it — read the frames the report names. → docs/hooks/system.md · docs/prd.md §282
- **A `private` nested type reached from another file ONLY through a signature type-checks, then crashes swift-frontend (prd §718).** Moving FeedScreen's wallet room to an extension file left `RunPosition` private; the moved code never names it, only calls `cardRunPositions` (which returns `[RunPosition]`). LLVM's verifier died on *"Global is external, but doesn't have external or weak linkage!"* with no diagnostic naming the fix. Open every nested type a moved signature mentions, and a harness that reads a split file by path must read every half → prd §718

## A container that has not been sized proposes a PLACEHOLDER, and a `List` cell born there keeps it (prd §805, 2026-09-17)

**Symptom.** For ten frames (~0.3s) of every cold launch, the feed drew in a column
149pt wide on a 402pt screen — the cover card clipped mid-word, the day divider
squeezed — then snapped to full width. It read as "the app loads wrong for a second".

**What it is not.** Not slow layout, not a slow fetch, not the theme flip, and not the
shell: `RootShell` and `MainSurface` measure **402 on their first layout pass**. A width
probe placed at four depths found the `NavigationStack` handing its root content **36**,
and the pager's `ZStack` and the feed's `List` being BORN in that pass. The container
corrects to 402 forty milliseconds later, before anything is painted — so the container
was never what the person saw.

**What it is.** SwiftUI's `List` is a `UICollectionView`. Its first cell self-sizes
against the container it was born in, and that stale size **survives the container's
correction by another ~250ms**, because a cell is re-measured only when something forces
one. At launch the thing that forces one is the first sweep landing. The head row was
measured at 4pt (36 minus its insets), then 156, and reached its real 311 only 371ms in.

**The fix.** Upstream of the `List`: hand the room a width that is right in the FIRST
pass. A `GeometryReader` around `MainSurface.surface` is the only thing that reads a real
width in the same pass it proposes one — `.onGeometryChange` writes `@State`, which lands
a pass late, and that pass is the one that already corrects itself. `pinnedRoomWidth(_:)`
subtracts the two columns reserved outside the pinned frame (the rail's leading padding,
the detail pane's trailing inset), both derived from the measured width rather than from
`surfaceWidth`, or the same one-pass-wrong layout simply moves to iPad. Nothing is pinned
before the reader has a size.

**The rule.** Anything that measures once and caches — a `List` cell, a `ViewThatFits`
candidate, a `containerRelativeFrame` — will keep a placeholder width until something
else invalidates it. Where a screen must be right in its first painted frame, the width
comes from a reader in the same pass, never from state written during it.

**How it was found, and how to find the next one.** By recording the launch at 30fps and
measuring the content's right edge per frame, then adding a four-level width probe — not
by reasoning about the layout. Reasoning had three plausible wrong answers ready
(`dsAdaptiveContentWidth`, the pager's `pagerFrame`, a room snapshot). The same recording,
re-run after the fix, is the proof: zero narrow frames, the `List` born at 402.

## `onAppear`/`onDisappear` in a `List` track CELL RECYCLING, not the viewport (prd §864, 2026-09-20)

A row's lifecycle callbacks fire when the collection view creates and releases its cell,
which lags the viewport by roughly a screen in each direction. **Anything that means "is
this row being LOOKED at" must use `onScrollVisibilityChange`** (iOS 18+), which answers
that question and no other.

**What it cost.** §864's demo lead and the demo capsule are mutually exclusive: while the
lead is on screen it IS the marking and the capsule stands down. The flag was written from
`onAppear`/`onDisappear`, so scrolling the lead just out of sight left it true — the capsule
stayed down over a fake $12,480 crown and 68 rooms of somebody else's life, with **no
marking anywhere on screen**. That is §83's continuous marking failing in exactly the place
the feature exists to fix, and nothing could see it: it builds, it renders, and both states
are correct in isolation.

**The general shape.** A lifecycle callback answers "does this view exist", and a lot of
code wants "can the person see it". They agree at rest and diverge under a finger, which is
why this reads as an intermittent bug rather than a wrong API. `demo-marking-audit.py`
check two fails a flag raised from `onAppear`, with the mutation to prove it.

Found by review, not by running it.
