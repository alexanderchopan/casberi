# The SwiftData liveness class — reading a deleted `Thing`

**Moved out of `CLAUDE.md` verbatim on 2026-09-08 (prd §654b), not rewritten.** It
was ONE 12,090-byte line — 12% of the rule sheet's whole budget — and the rule
sheet's own header says long-form goes to `docs/`. Nothing here is new, nothing
is summarised, and no corollary was dropped: the text below is the line as it
stood, with the six corollaries split onto their own paragraphs so they can be
read. `CLAUDE.md` keeps the rule and a pointer.

**Why it is this long, and why none of it may be trimmed:** every corollary is a
SHIPPED CRASH, and each one was reached only after the previous fix looked
complete. Builds 137/138/139, 142, 150, 176, 177, 188 and 250 are all in here.
The mechanical enforcement is `scripts/swiftdata-liveness-audit.py` (checks 1–6),
whose findings each name the build that taught them.

---

**Never key a `ForEach` on a persistent `@Model` property from a DERIVED array — the perpetual "crashes on different screens after an update/first sync" class (builds 137/138/139, 2026-07-24).** Reading any stored `Thing` property (`id`, `title`, `source`, `capturedAt`, …) after that `Thing` is deleted/invalidated traps inside SwiftData (`_assertionFailure` → EXC_BREAKPOINT, stack: `ForEachChild.updateValue()` → Casberi → SwiftData). SwiftUI re-reads each element's `id` during identity diffing on EVERY graph update, including the exact transaction a delete lands. The app deletes `Thing`s constantly on the MAIN context while the UI is live: `SyncReconcile.dedupeBySourceRef` at launch (collapses CloudKit-merged duplicates) + a per-foreground heal in nearly every bridge (Photos/Calendar/Reminders/Contacts/HomeKit/OneClaw/Bluesky/Farcaster/Mail — each `context.delete`s upstream-gone rows), plus CloudKit-propagated deletes. A `ForEach` **directly over a `@Query` array is coordinated by SwiftData and safe**; a `ForEach` over a `.filter`/`.map`/day-grouping/`@State`-held array holding raw `Thing` refs is NOT — that derived case is the whole crash surface, and it recurs on every screen that has one (feed, wallet Worth-a-look tray, wallet history, Tokens/Stocktwits/Kalshi watchlists, address-book card, the shared `RecentThingsSection`). THE RULE: iterate `things.keyed` (`Screens/ThingRowKeying.swift` — a `KeyedThing` value wrapper capturing `id.uuidString` while the model is valid) and read `$0.thing` in the body; an enum row type must store its id (`case approval(id: String, thing: Thing)`), never compute it from `t.id` lazily. For a HELD reference (a `Thing` in `@State`, captured in a closure, or bound to `sheet(item:)`/`navigationDestination`) guard with `thing.isLive` (same file) before reading a stored property, since a delete can land under an open sheet/dialog. A fresh install is NOT immune — it still imports the iCloud zone (duplicates and all) then dedupes them. This is NOT the SwiftUI "reused id" trap (that asserts in SwiftUICore with no SwiftData frames).

COROLLARY (build 142, 2026-07-24): the guard for the HELD case must not `dismiss()` from `onAppear`. `ThingSheetView`'s `if thing.modelContext == nil { Color.clear.onAppear { dismiss() } }` converted the SwiftData read-trap into a UIKit crash — dismissing DURING the sheet's (zoom) present transition trips `brk 1` inside `-[UIPresentationController runTransitionForCurrentStateAnimated:]` (reached via SwiftUI `SheetBridge.preferencesDidChange`; the empty branch also drops the `.presentationDetents` the sheet expects, which pokes `preferencesDidChange`). Symptom: "opened a Bluesky post and it crashed" — a post Bluesky's own foreground delete-sync heal (`BlueskyIngest.heal`) removed between tap and present. Fix: wait for the transition to settle before dismissing (`Color.clear.task { try? await Task.sleep(.milliseconds(500)); dismiss() }`), and guard the sheet's CHILD views (`SocialPostContent`) with `thing.isLive` too — the parent's synchronous init/body guard doesn't cover a child that SwiftUI re-renders on the model's own observation before the parent re-evaluates.

**COROLLARY 2 (build 150, 2026-07-25):** **keying the `ForEach` is only half the fix — anything else that reads the same derived array is still exposed.** A pull-to-refresh crash symbolicated (`atos` against the archive dSYM) to `FeedScreen.countLabel` inside `daySection`'s own SECTION HEADER: the rows were correctly keyed, but the header did `Set(rows.map(\.kind))` over the raw day-grouped array, and `cardRunPositions` read `standsAlone(rows[$0])`/`rows[$0].id` beside it. A refresh runs every bridge's heal, so a delete lands inside the same graph update that re-evaluates the section, and the first persisted read on a tombstoned model traps — same `_assertionFailure` → SwiftData → Casberi stack, no `ForEachChild` frame needed on the Casberi side. THE RULE: filter a derived array to `filter(\.isLive)` ONCE at the top of the view that owns it, before positions, rows, headers or footers read through it — and guard shared helpers that take `[Thing]` (like `countLabel`, called from both a header and the caught-up footer) independently, since their other call sites hand them their own derived arrays.

**COROLLARY 3 (build 176, 2026-07-28): keying and pre-filtering are BOTH insufficient — the row body itself must re-check.** `ForEachChild.updateValue()` re-evaluates the CONTENT closure against the array the `ForEach` value ALREADY HOLDS, under its own `ObservationCenter` callback, when a tracked model changes — the parent body has not re-run yet, so that array still contains the row just deleted. So the upstream `filter(\.isLive)` of corollary 2 is not a guard for the body: it ran when the view value was made, which is BEFORE the delete. Build 176 crashed on first open exactly there — day rows correctly keyed (`FeedRow.id` a captured `String`), header correctly filtered, checks 1 and 2 both green — trapping one frame later on `thing.kind` inside `FeedScreen.shapedRow`. THE RULE: a `ForEach` content closure re-checks liveness INSIDE the closure before its first stored-property read — `if let thing = row.live { … }` (`KeyedThing.live`) — and that includes reads in the ARGUMENTS of a row-builder call (`imageOnly.contains(thing.id)`), which are evaluated at the call site and therefore beat any guard the builder does internally. Now mechanical: the liveness audit's CHECK 3 flags a content closure that reaches `.thing` with no `isLive`/`.live` inside it (mutation-tested against build 176's own crash site). Its deliberate limit — it triggers on `.thing`, so a `Thing` bound out of another wrapper is invisible — is why `FeedScreen.FeedRow.single` carries a `KeyedThing` rather than a raw `Thing`: keep new row wrappers in the shape the lint can see. Two duplication traps this crash paid for: `FeedScreen` had a PRIVATE copy of `KeyedThing` that shadowed the shared one and never gained `live` (now deleted, one type), and its doc asserted the false premise ("bodies only ever render the post-delete `@Query` snapshot") that made the whole class look solved.

**COROLLARY 4 (build 177, 2026-07-28) — the ROOT the other three were symptoms of: do not hand a held `[Thing]` onward on the PROMISE that downstream readers guard.** Build 177 crashed with no `ForEach` frame at all — `FeedScreen.feedList` → `List.init(content:)` → `themesLedeSection` → `HomeComposition.projectClusters` reading `thing.tags`. The source is `visible`, which for the unfiltered All room returns `debouncedAllSnapshot` (`@State private var … : [Thing]?`, the 2026-07-28 perf debounce) — raw model refs held across a debounce window, so DELIBERATELY behind the live corpus: not a narrow race but a window that stays open after every delete. The comment above that property claimed "every downstream reader already re-filters `.isLive`"; that was never true, and both 176 and 177 are the same stale array reaching two different unguarded readers. THE RULE: filter `.live` AT THE BOUNDARY — the computed property or accessor that hands the array out (`visible`, `merged`, `orderedWatched`) — so the guarantee is local and provable, not a cross-file promise; and guard SHARED helpers that take `[Thing]` internally too (`for thing in things where thing.isLive`), since they're reached from several callers. Mechanical as CHECK 4: a `@State`-held `[Thing]`/`[Thing]?` returned or passed onward whole without `.live` is a finding (verified against build 177's own line). It is deliberately narrow — hand-off only, one finding per array, comments stripped and shadowing rebinds skipped, since its first draft fired 15 times on one screen — with a documented `HANDOFF_OK` escape hatch for the one case where filtering would misalign `IndexSet` offsets. Note a shadowing rebind (`let posts = posts.live`) HIDES the guard from the audit: spell `.live` per use instead. Two audit defects this found: `GenUI/` was never in `SOURCES` at all (the crash file lives there), and CHECK 3's `.thing` trigger matched `.thingID` as a substring (now `\.thing\b`).

**COROLLARY 5 (build 188, 2026-07-29) — THE LEAF, and the deepest form of the class: corollaries 1–4 are all about the CONTAINER, and a container guard only stops a dead row being CREATED.** SwiftUI re-evaluates a leaf view's body on the MODEL'S OWN observation through that leaf's own attribute node (`DynamicBody.updateValue` → `ViewBodyAccessor.updateBody`), with no involvement from the parent that built it — so a row ALREADY in the tree is untouched by anything the parent does. Build 188 crashed there with no `ForEach` and no `List` frame: `BandRow.body` → `mailSender` → `thing.kind`, re-run inside a `UICollectionView` batch update while the source pager animated (`PagingCollectionView.apply(changes:)` → `_UIHostingView.layoutSubviews`). Keying was right, the ForEach-closure guard was right, the boundary filter was right, and **none of them were in the crash path**. THE RULE: a `View` struct that stores a `Thing` guards its OWN body — `var body: some View { if thing.isLive { liveBody } }` with the original body renamed to `@ViewBuilder private var liveBody` (no re-indenting, and no extra view-tree depth since it's a computed property, not a wrapper view). This was ALREADY the build-142 lesson recorded above ("guard the sheet's CHILD views … the parent's guard doesn't cover a child SwiftUI re-renders on the model's own observation") — scoped to two sheet views and never generalised to the **25** row/content views that had the identical shape (`BandRow`, `TokenRow`, `PostCard`, `PhotoWell`, every `ThingContent`/`ThingStage` view, `WalletHistoryRow`, `LiveStreamHero`, …), all now guarded. Mechanical as CHECK 5: a `struct X: View` with a stored `Thing` property and no `isLive`/`.live` anywhere in the struct is a finding (mutation-tested — it names `ShapedRows.swift:20 BandRow`, 188's own crash site). Read the whole corollary chain together: 3 and 4 are about who hands the model over, 5 is about who reads it, and 5 is the one that holds when the parent isn't running at all.

**COROLLARY 6 (build 250, 2026-08-03) — the class ESCAPES THE VIEW LAYER: a `[Thing]` held across an `await` is stale on resume.** Corollaries 1–5 are all about SwiftUI, and none of them can reach async model code. Build 250 crashed five times in ninety minutes (twice with the app backgrounded/locked, so no view was rendering at all): `RootShell` → `await TodayBrief.compose(things:)` → `moneyHero` reading `$0.kind` on a deleted `Thing`. `compose` captured `things`/`landed`, then suspended on its three live reads — **bounded at `liveReadBudget`, so up to 8 SECONDS** — and the app's own foreground bridge sweep deletes Things in exactly that window. It surfaced then because `RootShell` had just started composing the brief UNCONDITIONALLY on every foreground (to keep the widget fresh); before that it ran only for someone who had KEPT the "today" ask, which most people never do, so the path was rare. THE RULE: an async function handed a `[Thing]` re-filters `.live` AFTER each suspension — and on ENTRY too when its own caller awaited before handing the array over (`KeptAskStore.refreshDigests` awaits `KeptAskComposers.compose` once per kind in a loop while holding one array, so by the third kind it can be passing tombstones). Filtering once after the last `await` is sufficient ONLY because these composers are `@MainActor` and have no further suspension — the remainder then runs with exclusive main-actor access, so nothing can delete between the filter and the reads; drop either condition and the guard must move next to each read. Mechanical as CHECK 6: an `async` func taking a `[Thing]` that reads a stored property after its last `await`, with no `.live`/`isLive`, is a finding (mutation-tested — it names `TodayBrief.swift:117 compose`, build 250's own crash site). `Casberi/Casberi/Model` joined the audit's `SOURCES` the same day; checks 1–5 are view-shaped and simply find nothing there, which is why the whole directory had gone unaudited.
