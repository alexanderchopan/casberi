# Keyed and keyless bridges

Moved out of `CLAUDE.md` on 2026-09-05 so the always-loaded file stays a rule sheet.
Every entry below is **verbatim** as it was written — nothing was summarised, shortened or dropped.
`CLAUDE.md` carries a one-line index pointing here, keyed by the hook flag or the entry title.

- `-oembedProbe <url>` — ask an allowlisted host what a saved link IS, keylessly (prd §244, `Model/OEmbed.swift`), and NSLog every field it answered with: provider/author/thumbnail, then the title and the `enrichedText` the link would land wearing (three NSLogs, not one — the `-todayProbe` truncation lesson). Reads `handled=NO` when the host isn't in the table and `FAILED` when it is and the endpoint didn't answer — different bugs, so they read differently. This is link ENRICHMENT, not a bridge: nothing connects, nothing syncs, there is no catalog seat and `catalog-sync.sh` has nothing to check. It exists because the generic path (`LinkTitle.enrich` → `ProductMeta`/`fetchPage`) reads a page's `<head>`, and some sites serve a non-browser client no usable head at all — a TikTok link used to land wearing the site's stock page title with no thumbnail and no creator, while every other link in the corpus got a real face. `OEmbed.endpoints` is an ALLOWLIST by design (TikTok/YouTube/Vimeo/SoundCloud/Spotify/Flickr): the spec's `<link rel="alternate" type="application/json+oembed">` discovery would need the page fetch this path exists to beat, and would let any saved URL name an arbitrary host for us to call. Host matching is on the label boundary (`== suffix` or `.hasSuffix("." + suffix)`), never `contains` — `tiktok.com.attacker.example` must not match. A hit RETURNS from `enrich` rather than falling through, or the page fetch would overwrite the good title with the stock one. **UNMEASURED (2026-07-31): authored on Linux with no Xcode and no egress to any of these hosts — never compiled, never run.** Every endpoint is doc-derived and every failure path returns nil to the existing behaviour, so it fails safe; probe each host before trusting it. Why TikTok gets this and not a seat: their export is 1–4 days stale (declined, prd §36, unchanged), they have never had RSS (the generators are scraped, the Duolingo decline), the Display API reads only the authenticated account's own posts, and the EEA Data Portability API needs the post-M2 server.

- **Watching a PERSON on GitHub (prd §519, 2026-08-29):** `-ghWatchPerson "<username|@username|profile URL>"` watches somebody headlessly, `-ghPeopleProbe YES` reports the pass person by person. The seat could mirror your stars and subscriptions and privately watch a repo (`GitHubRepoWatch`, 2026-07-16) and had NO way to follow a person — while `/users/<login>/events`, the endpoint that answers "what has this person been doing", was already in the file, called once, for the token's own account (the `contributions` feed). Built as `GitHubRepoWatch` is rather than as `PUT /user/following/<login>` because **following on GitHub is PUBLIC and it NOTIFIES**: a Casberi watch is tracked on this device, so watching a maintainer, a competitor or somebody you are about to hire appears nowhere and tells nobody. The watch IS the thing (TokenWatch precedent) — it lands as proof, deleting it unwatches it. **A REPO URL IS REFUSED, NOT READ AS ITS OWNER** — `github.com/torvalds` and `github.com/torvalds/linux` differ by one path component, and reading the owner out of the second is a watch that resolves, lands, and syncs forever while being nothing anybody asked for; `GitHubLinks.personLogin` takes exactly one path component, a bare login or an `@login`, and validates GitHub's own alphabet, which is the one rule here that is SECURITY rather than manners (the login is interpolated straight into `/users/<login>/events`, so a `/` or a `..` reaching it addresses an endpoint nobody asked for). **`webURLPathParts`/`repoPath(fromWebURL:)` MOVED from `GitHubFeedFetch` into the new Foundation-only `Model/GitHubLinks.swift`** — a move, not a copy, because two readings of one URL drift and then a repo link and a profile link disagree about which host they trust; the move also buys the repo parser the coverage it never had, since `GitHubFeeds.swift` touches `Thing` and no harness can compile it. **ONE EVENT, ONE ROW**: a watched person's activity and your own contributions go through one builder (`eventThing`) under the shared `gh:event:<id>` ref, so an event this app can reach twice lands once (`TokenIngest.refresh` inserts each ref into `existing` as it goes, so it holds within a pass too); `GitHubLinks.activityLogins` drops your own account ONLY when the contributions feed is on — dropping it unconditionally makes watching yourself with that feed off read nothing forever, never dropping it reads one endpoint twice a sweep. The tag is **`Activity`, never `Contributions`** (that feed's blurb says "your own" and means it; the row stamps `authorHandle`/`authorAvatarURL` and `GitHub` is in `ShapedRows.faceSources`, so WHO is already on screen — the one deliberate divergence from the repo watch, which still files the owner's avatar as the row's ART and is left alone because fixing it needs a heal). **One request per watched person, and the commit-message follow-up is deliberately NOT made**: that cap is 15 for ONE account and would multiply by the number of people watched. No new `Thing` field (**no CloudKit deploy**), no new host. `-ghPeopleProbe` exists because **`0 landed` is the HEALTHY answer** with five causes that render as one silence — nobody watched, no token, the only watch is YOU with contributions on, a quiet account, or GitHub refusing the endpoint — and only the last is a bug; it prints TITLES, not a count, because a count cannot show the wording came out right. Guarded by `scripts/github-person-selftest.sh` (in `verify.sh`), which compiles `GitHubLinks.swift` WHOLE — 51 assertions, 10 mutations, plus drift guards that the two watch ref prefixes stay non-overlapping (`watchedRepos` and `watchedPeople` scan the same rows), that `activityTag` collides with no feed's tag, and that `eventsFor` never reaches `commitMessage` (read from a COMMENT-STRIPPED copy — both files document these rules by naming what they must not do, the Obsidian/Cursor lesson). **UNMEASURED against a live account** — no GitHub token is stored on this host, so no watch has ever resolved and no events feed has ever been read; every read is a GET returning nil on failure and a person whose feed fails contributes nothing rather than failing the refresh.

- **Feeds (RSS + the four feed-follow bridges), prd §312, 2026-08-06.** `-feedFollow "<Substack|Reddit|YouTube|Podcasts>:<name[,name]>"` — follow names on a feed-follow bridge and sync, NSLogging one `feedFollowRow|` per entry with its resolved feed URL AND its learned title. **These four seats had NO headless door at all before this**, which is why the resolver bug below could never have been caught by an automated run; the URL/title PAIRING is the tell, since a wrong resolution still returns a real feed full of real videos and only the title reads as wrong. `-feedHealthProbe YES` — every tracked feed's HTTP record (`FeedFreshness`), one `feedHealth|` line each: last OK, failure streak, last status, and `cond=` (are validators stored). The conditional GET is INVISIBLE when it works — a 304 lands exactly what a 200-with-nothing-new lands — so `cond=` is the only place it's observable, and `status` separates 304 (working), 404 (moved, or being throttled) and 0 (offline). `-articleTextProbe [limit]` — the reader pass over RSS/Substack rows (`FeedArticleText`), one `articleText|` per row; its whole output is `enrichedText`, retrieval-only by the 2026-07-15 ruling, so a successful read and a read that never ran render identically on every screen. `-ytChannelProbe <@handle|url|id>` — resolve a YouTube name and fetch the feed that id serves, logging the id AND the feed's own `<title>`. `-ytRepairProbe YES|force` — re-resolve every stored YouTube follow (`YouTubeFollowRepair`); `force` ignores the done flag. `-ytShorts <limit|YES>` — classify landed YouTube rows Short-vs-video (`YouTubeShorts`), one `ytShort|` each.
  - **THE SHIPPED BUG: following an `@handle` on YouTube followed SOMEBODY ELSE.** `FeedFetch.resolveYouTubeChannelID` read the first `"channelId"` in the channel page — which belongs to another channel in the page's initial-data blob. Measured 2026-08-06, wrong 3/3: `@MrBeast` → `UCAiLfj…` (real `UCX6OQ3…`), `@mkbhd` → `UCG7J20…` (real `UCBJycs…`), `@veritasium` → `UCin0m1…` (real `UCHnyfM…`). The function's OWN fallback (`channel/UC…`) was correct all along and was never reached. It failed invisibly — a real feed, real videos, the wrong channel's real name as the learned title. Now `rel=canonical` → `"externalId"` → `channel/UC…`, and the naive read is DELETED rather than demoted (it never answers correctly). Guarded nightly in `live-integrations.sh`, including a row that warns if the naive read ever starts AGREEING — so the fix can't be quietly reverted by someone who finds `"channelId"` and assumes it means this channel. `YouTubeFollowRepair` fixes follows already stored: it re-resolves the person's own input and compares, so a difference is PROOF rather than an inference, and prunes the stranger's rows only in that proven case (else `removeName`, which prunes by the CURRENT learned name, could never explain them again). It withholds its done flag until every follow has answered.
  - **YouTube answers a throttled client a plain 404, not a 429** (measured: the same channel id served a full 200 and then 404ed for ~20 minutes across three channels). So a 404 is NOT evidence a channel is gone — hence `FeedFreshness`'s three-miss floor before a health line, the repair's refusal to mark itself done on a silent pass, and the nightly's amber-not-red on an empty feed.
  - **Conditional GET pays off UNEVENLY, measured 3 of 7 feeds:** TechCrunch serves ETag + Last-Modified (verified end-to-end — 304 and 0 bytes vs 200 and 17,250), the Verge and a Ghost blog serve an ETag; **BBC, Hacker News, Reddit `.rss` and YouTube `videos.xml` serve NEITHER** — so the feed-follow bridges' two biggest hosts get nothing from it. A feed with no validators costs what it always did, so it's free either way, but don't count on it. The record lives in UserDefaults and **could not have lived on `RSSStore.Feed`/`FeedFollowEntry`**: both are `Codable` decoded with `try?` falling back to an EMPTY list, and Swift's synthesized decoder does not apply defaults for a missing key — adding a field would have silently unfollowed every feed on the device. Validators are dropped once a day on purpose: a 304 hands the ingest nothing, and both ingests HEAL already-landed rows from feed data every pass, so a permanently-304 feed would stall those forever.
  - **Nothing in a YouTube feed says a video is a Short** — every entry's `media:content` is a fixed 640×390 flash placeholder and every thumbnail a fixed 480×360. The only keyless read is what `/shorts/<id>` answers: **200 = Short, 303 → `/watch` = regular** (measured 4/4, then in-app 6 asked → 4/2/0 unclear). HEAD, so zero bytes, and redirects REFUSED — following the 303 answers 200 from the watch page and silently inverts the classification for every row. Only Shorts are tagged (`Shorts`, a §308 facet); a `Video` tag on the other 90% is chrome.

- **Telegram, through the two doors §57 never weighed (2026-08-23, prd §456).** The seat §57 REMOVED on 2026-07-14 returns, and its own closing line ("if Telegram ever returns it re-enters this decision from scratch") is why. Bot API and TDLib are still refused for §57's reasons. What that ruling never weighed: **a public CHANNEL is not a chat** — it is broadcast media with a public web page, so following one is the §312 feed-follow shape, not MTProto. And the export door was declined on "nobody wants to import their chats", a premise this app's own nine import bridges have since overturned; the strongest case is **Saved Messages**, the pile of links people send themselves.
  - **ONE seat, ONE source, and the rule that made it possible.** The halves want opposite things from All — a followed channel is a drip that belongs there, an export is tens of thousands of rows that must not — and `bulkImportSources` is per-SOURCE. **The ruling (user): split by REF PREFIX.** `Corpus.liveRefPrefixes` + `arrivedLive` let `telegram:post:` into All while `telegram:chat:`/`telegram:saved:`/`telegram:channel:` stay out. The distinction is already on every row, so **no new `Thing` field and no CloudKit deploy**, and it cannot drift the way a landing-time flag could. The other four bulk sources declare no live prefix and are untouched. **Corollary that would have been missed:** `ImportRemoval` is source-scoped, so "remove this import" would have deleted your followed channels — both halves now step over the live rows, and the walk uses an OFFSET rather than a filter, because filtering alone breaks the loop the moment one page is all live rows and silently leaves every imported row beyond it in place.
  - **The parse is SCRAPE-GRADE with no contract, so it was measured before it was written.** Eight real channels, and a throwaway reference parser earned its keep immediately by reporting **19 of 20 posts**. Seven rules, each a silent wrong answer that renders perfectly: (1) **`/s/<name>` answering 200 IS the definition of a followable channel** — a 302 means it is not one and the LANDING page says which ("subscribers" = preview off, "members" = a GROUP, neither = unclaimed), three answers that would otherwise be one empty room; (2) **posts arrive OLDEST FIRST**, so the ingest's `prefix(15)` takes the fifteen oldest unless the mapper REVERSES them — the room fills with everything except today; (3) **slice BETWEEN wrapper starts**, since a lookahead needing a following wrapper drops the final (newest) message; (4) **the text container can NEST a `<div>`** (1 post in 19), so its end is found by depth or those posts truncate mid-sentence; (5) **`telegram.org/img/emoji/…` is a DECOY** — every emoji is an `<i>` whose `background-image` is a sprite, so the naive read files every emoji as a photograph; only `telesco.pe`, matched on the label boundary; (6) **"Please open Telegram to view this post" is CHROME**, not the author's words; (7) **the view count is REFUSED** — published already rounded ("12.6M") against an `Int` field, so landing it fabricates precision (§83; YouTube's `media:statistics` is exact and IS landed). Two more found only by RUNNING it: a `<time class="message_video_duration">` with no `datetime` sits BEFORE the real timestamp (left 15 of 20 posts undated, and an undated post falls back to "now"), and `forwarded_from_name` is an `<a>` on a public source and a `<span>` on a private one — so the enclosing tag is INFERRED from the markup rather than passed in. Keyless, UA-insensitive (bare curl gets the full page), no rate limit across a burst — but that was measured with fresh connections per request, so the Farcaster keep-alive lesson still applies and the fetch is paced.
  - **The export is frequently INVALID JSON, and nothing else would have said so.** Telegram's own generator escapes control bytes as `\xNN`, which RFC 8259 does not permit, so `JSONSerialization` fails on the WHOLE file with no partial result — `TelegramExport.repairControlEscapes` is a pre-pass, not a nicety, and it is the single most likely reason a real archive fails. Also encoded: `text` is polymorphic (bare String or an array mixing strings and entity objects) while `text_entities` is monomorphic and preferred; `date` is local time with NO offset in a zone the file never records, so the quoted-STRING `date_unixtime` is authoritative; **both are ABSENT pre-2021**; `type` has a third value `unsupported` carrying no date and no text; a SINGLE-CHAT export is a bare chat object whose media paths lack the `chats/chat_NN/` prefix; media placeholders can be name-PREFIXED so they are matched as substrings; ids are unique per CHAT, not globally.
  - Probes: `-feedFollow "Telegram:<@handle>"` (the generic arm — no new hook needed), **`-telegramChannelProbe <@handle|t.me link>`** (an empty room has FIVE causes that render as one silence — not a channel at all, preview off, unreachable, genuinely quiet, or the markup moved — and only the last is a bug), and `-telegramImport <path>`. `scripts/telegram-selftest.sh` compiles `TelegramChannel.swift` WHOLE; `live-integrations.sh` asserts the six markers nightly, because when a scrape's markup moves the room does not break, it goes QUIET. **The live half is MEASURED against eight channels; the import half is UNMEASURED against a real export** — none has ever been held by this project — so it fails safe throughout.

- `-kalshiBookProbe YES` — the Kalshi browse room's read, PHASE BY PHASE (prd §287, 2026-08-03, `KalshiWatch.diagnose`). One `kalshiBook|` NSLog per line (the `-todayProbe` truncation lesson): discovery HTTP status + event count + how many carry `event_ticker`, the categories parsed, then per hydrated event its market count, its quoted count, and — the decisive field — the price-shaped keys ACTUALLY ON THE WIRE, ending with the room's own `book("")` outcome. - Dropbox (2026-07-27, `Model/DropboxBridge.swift`, `Screens/DropboxScreen.swift`) — a first-class Storage seat beside Files, reading Dropbox's own API (`api.dropboxapi.com`) instead of a local folder bookmark, so it works without the Dropbox app installed. **GATED until a client id exists**: `DropboxAuth.clientID` is empty — register a free Scoped Access app at dropbox.com/developers/apps (permissions `files.metadata.read` + `files.content.read`, redirect URI `casberi://dropbox-auth`) and paste the app key in; a Dropbox app key is not a secret, PKCE needs nothing else.
