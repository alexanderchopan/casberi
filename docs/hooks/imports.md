# Bulk imports and local files

Moved out of `CLAUDE.md` on 2026-09-05 so the always-loaded file stays a rule sheet.
Every entry below is **verbatim** as it was written — nothing was summarised, shortened or dropped.
`CLAUDE.md` carries a one-line index pointing here, keyed by the hook flag or the entry title.

- **The journals' three shipped defects, fixed in the same pass (prd §398):** (1) **both importers silently truncated at 500 entries** — the §307/§309 class, in the two rooms nobody went back for; a journal is at most an entry a day, so 500 is thirteen months, and a truncated import and a complete one produced byte-identical receipts. `DayOneImport.entryCap` is 5,000 and the refusal is COUNTED (`Summary.dropped`, on the receipt, both screens and both probes, worded as X's "N older not imported"; named apart from `skipped` because "already here" is a re-import working and "not imported" is a run that left the oldest years on disk). Raising it tenfold created §310's risk, so both landings moved onto `ImportCommit` — a chunk is a commit, so a run that dies partway keeps what it landed. (2) **every note row read its first line twice** — `ExcerptRow` drew the title and then the whole of `content` beneath it, and every importer that names an entry after its opening line (Day One, Apple Journal, Obsidian, a shared Apple Note) stores that line as content's first line. **The guard for this existed and could never fire**: `text != thing.title` compares a raw body against `titleLine`'s flattened, 80-clamped, heading-mark-stripped output, which it almost never equals — and an entry whose first line ran past 80 characters could never match at all. `IngestSupport.bodyBelowTitle` is `titleLine`'s inverse and compares the NORMALISED first line. (3) **neither journal was in `ScreenshotTopics.topicSource` or `FeedInsight.topicMap`** — the two rooms in this app most literally "what you write about". Both registered (`.note`, `includeDomains: false` — §313's "a hostname is not a subject"), and the sweep runs from `BridgeRefresh` as well as at import, which is the half that matters: both importers dedupe on `sourceRef`, so healing only at import reaches nothing already imported (§320's lesson). **The journal exports' PHOTOGRAPHS land too** — Day One's `photos/<md5>.<type>`, Apple Journal's `Resources/` named by its HTML's `<img src>`, both as the same 480pt `ImportMedia` thumbnail every other picture here is. **Day One's picker accepts the FOLDER as well as the `.json`, and it has to**: a scoped grant on a file cannot read the directory beside it, so the `.json` pick could never have reached `photos/` whatever the parser did; both still import every entry and only the folder brings the pictures, which is the screen's one remaining slab note (Apple Journal's "Photos stay in the export for now" is DELETED, not reworded — it stopped being true and there is no choice left for fine print to govern). `ImportMedia.mediaIndex(in:under:)` is `xMediaIndex` generalised: ONE directory listing per import, keyed by basename WITHOUT the extension — not tidiness, since Day One's `type` is the export's word for the format and need not match the extension on disk, and Apple Journal's `src` depth is Apple's business. All UNMEASURED against a real export; every path fails safe (a stem that matches nothing yields no thumbnail and the row lands as before).

- **`-instagramImport` and `-xArchiveImport` are DELETED (2026-10-27, prd §1579)**, with their importers (`InstagramImport`, `XArchiveImport`, `XArchiveAccount`), `-xFaces`, `-xReplyContext`, the X archive's sweep heals (`x.healRoom`, `x.healLinks`, `x.faces`), `ImportOptions` and the import-only halves of `ImportMedia`. Their pages lost the export doors in §1577 and nobody had imported. X and Instagram are their live sign-ins alone (`-xLiveProbe`, `-igLiveProbe`).

- `-tiktokImport <path>` — import a TikTok export (the `user_data_tiktok.json` file itself, or a folder holding it), `-tiktokFaces <limit|YES>` — run the oEmbed face pass (prd §279, 2026-08-02, `Model/TikTokImport.swift`; screen `Screens/TikTokImportScreen.swift`, seat id `tiktok`). **This OVERTURNS §36 and §244, which both declined TikTok** because the export lands 1–4 days stale — fatal for a FEED, irrelevant for an IMPORT (nothing claims to be current; every row is stamped with when it happened). The other three doors stay shut: no RSS ever, a Display API returning only the authenticated account's OWN posts, an EEA-only DMA API. **The four-day link expiry is the argument FOR importing** — the export is perishable, the corpus isn't, the same reasoning behind `SnapchatImport`'s 7-day media fetch. **The one measured fact, and the feature nearly shipped broken without it:** the export writes links as `www.tiktokv.com/share/video/<id>/` — a DIFFERENT HOST from `tiktok.com` — and that form answers **400** at the oEmbed endpoint, so `OEmbed.handles` returns false for every imported row and enrichment silently never runs. `www.tiktok.com/video/<id>` (username-less!) answers **200** with caption + creator + cover, identical to the canonical `@user/video/<id>` form; `TikTokLink` rewrites every link to it, and `sourceRef` keys on the video ID so dedupe survives another link-shape change. Measured 2026-08-02, re-measure before "fixing". Lands saves/likes (bare links, ONE row wearing both tags — not Instagram's two rows, since here the overlap is most of the saves list), your own videos' captions, and your comments. **Naming is a SECOND act by ruling** (§246's split): the import is instant and offline, the face pass is one request per video — but unlike Snapchat's it is under NO deadline, since the videos don't expire the way the export does. NOT landed, deliberately: watch history (the export's largest list, and a record of what scrolled PAST you — the `snap_history.json` call), search history/followers/following (tallies), DMs (§245's abstention). No topic map for this room: its writing is split across two kinds (`.link` captions, `.note` comments) and `FeedInsight.topicMap` reads one — a map covering half the writing would be fake status; the room leads with "Who you save most" (on `authorHandle`, which the face pass stamps via `OEmbed.Response.authorHandle` ← `author_unique_id`) then "Your TikTok year". **UNMEASURED against a real export** — paths/fields come from four independent parsers, which is also where two structural facts came from: TWO SCHEMA ERAS (`Activity` vs `Your Activity` + `Likes and Favorites`, so each category tries candidate paths) and FIELD CASE THAT VARIES WITHIN ONE FILE (`CommentsList` is `date`/`comment`/`url`, `VideoList` is `Date`/`Link`/`Title`), so every read tries both cases. A missing category is a skip, never a failure.

- **X joined `OEmbed.endpoints` on 2026-08-02 (prd §280), and it is the inverse of the Instagram entry removed alongside it.** Measured 2026-08-02: an x.com post URL fetched with the app's own `safariUserAgent` answers 200 with ~210KB carrying **zero `og:` tags and no `<title>` at all**, so the generic path names an X link NOTHING and the row keeps its naked URL — while `publish.x.com/oembed` answers keylessly with the author, the handle and the post's own words. Instagram's `<head>` served a real `og:title` all along (so its entry was never load-bearing); X's serves nothing (so its entry is the only face an X link will ever have). Both payloads look alike — an `html` blockquote, no `title` — and the difference is what the blockquote HOLDS: Instagram's only text is "View this post on Instagram", X writes the post into the `<p>`. Hence `OEmbed.parse`'s blockquote fallback, which fires ONLY when `title` is absent so it can't change what the other six providers answer. Tags are stripped from the RAW html and entities decoded AFTER — flipping that order makes an escaped `&lt;b&gt;` somebody typed into a tag the stripper eats. `twitter.com` is carried beside `x.com` (saved links are old). No thumbnail: X has never served one.

- **The vault (Obsidian), prd §320, 2026-08-06.** `-obsidianVault <path>` connects a folder headlessly; `-obsidianProbe YES` reports ONE pass job by job (`obsidian|` per phase, then `obsidianNote|` per note — the `-todayProbe` truncation lesson) with each note's retrieval-body length, tags, wikilink count and the `obsidian://` URL it would open at. It exists because **`landed=0` is the HEALTHY answer for a vault already in, and it has five other causes** — nothing new, everything capped out and waiting, notes still downloading from iCloud, the one-time reader repair still draining, or a walk that returned nothing — and only the last is a bug. **Three defects shipped from 2026-07-08 until this date, all invisible:** the cap was applied BEFORE the already-landed filter, so a vault over 100 notes could never finish arriving (**`FilesIngest` had the identical line** — fixed in the same commit; §307's silent-truncation class); a note was read ONCE and never again, so edits never landed; and deletions/renames never synced. Also fixed: the reader took the first 300 RAW bytes, which for any vault using templates/Dataview/the tag pane is `---\ntags: […]` and not one word the person wrote. **`capturedAt` is the read watermark** (it is already the file's own mtime — no new `Thing` field, no CloudKit deploy), and its one blind spot is why `ObsidianIngest.readerEpoch` exists: an unedited note is untouched by definition, so a change to how we READ notes reaches nothing on an established vault (§313's `termsEpoch` shape, done-flag keyed by the date so a bump re-arms it; withheld while anything is capped out or still downloading — `YouTubeFollowRepair`'s rule). The single-flight is TIME-BOXED now, not a bare `Bool`: `String(contentsOf:)` on an evicted iCloud note blocks with no timeout, so the `defer` never ran and the flag latched the bridge dead for the life of the app (`FilesIngest`'s own 2026-08-02 report — in the bridge whose setup copy says vaults live on iCloud Drive). The prune keeps `ScreenshotIngest.pruneDeleted`'s empty-read guard for the same reason: **an un-materialized iCloud folder enumerates EMPTY**, and reading that as an emptied vault deletes the corpus and mirrors it everywhere. Notes now carry their full body on `enrichedText` (retrieval-only, nothing draws it) and the vault's own frontmatter/inline tags on `tags`; an edit clears `embedding` AND `topicsAt`, since a "we looked" mark is not a "we looked correctly" mark. Two features existed and NOTHING CALLED THEM: `NoteMoments.checkLinkCrossings`/`checkWikilinkReachBack` (shipped 2026-07-28, never once reached) and the room's absence from `ScreenshotTopics.topicSource` + `FeedInsight.topicMap`, which left the app's most literal "what you write about" corpus leading with a year heatmap. `TopicSource` gained a `text` closure — every room before this kept its whole text on `content`, and a vault note does not. Added: "Open in Obsidian" (`obsidian://open?vault=&file=`, both halves already stored, gated on `canOpenURL` so it can never be a disc that does nothing) and BACKLINKS in the sheet. `scripts/obsidian-selftest.sh` compiles `Model/ObsidianNote.swift` WHOLE and unmodified (Foundation-only by design) — 76 assertions, 11 mutations, plus drift guards for both cap orderings; its first run re-earned §319's lesson, firing against the FIXED source because both files describe the old broken line in a comment, so negative guards grep a comment-stripped copy.

- **The folder a file is saved in, prd §408, 2026-08-19 (user feedback: "would be great to be able to press here and it takes you to folder where the file is saved").** `-filesRevealProbe YES|"<title prefix>"` — what the thing sheet's "From" row SAYS for a folder-picked file and where pressing it lands: the scheme census (`claimed` is ground truth, `inSet` is what the verb is gated on), whether the bookmark still resolves, then per row the ref, the words, the URL and the discs (one NSLog per fact — the `-todayProbe` truncation lesson). **Two things were wrong with that row and both were invisible**: it read "in your folder" for every file in the corpus however deep it sat, and it was a label, not a door — a folder-picked file was the one bridge here whose rows exist somewhere else and had NO way through (a cast has its thread, a note its vault, a transaction its explorer). Now "in Receipts" (`FilesLocation.folderName` — the IMMEDIATE parent, since "in Documents/2026/Q3/Receipts" is a field value wearing a preposition; the connected folder's own name for a file at its root), and both the row and a new "Show in Files" disc open the Files app AT THAT FOLDER. **The scheme is UNMEASURED and that is the honest grade**: iOS publishes NO public API that reveals a file, so this rides the Files app's own undocumented `shareddocuments://` — the `photos-redirect://` grade, one app over — gated on `canOpenURL` with the scheme in `LSApplicationQueriesSchemes`, so it can never be a disc that does nothing and simply is not there on Mac Catalyst. Worst case for a wrong path is the Files app's own root, which is why the probe prints the exact string handed to LaunchServices; measure it on a device before trusting the folder half. **The folder, never the file** — a file path opens a preview of the thing you are already looking at. **Scoped to the Files SOURCE, not the `.file` kind**: Dropbox lands `.file` rows whose bytes are not on this device. The path is rebuilt from the ref, which `FilesIngest.WalkedFile`'s doc forbids for a READ and is safe here for the reason that doc gives — nothing is read, the string is handed to another app, and a fresh walk would be an iCloud-blocking enumeration on a tap. Fenced against `..` (a ref goes through a `Thing` and a CloudKit round trip before it builds a URL). Costs nothing: no new `Thing` field, no request, no CloudKit deploy. `Model/FilesLocation.swift` is Foundation-only by design and `scripts/files-location-selftest.sh` compiles it WHOLE (39 assertions, 7 mutations, plus drift guards for the three gates, both verb dispatchers, and the negative that the hand-off never takes the pasteboard on its way out — read from a COMMENT-STRIPPED copy, since the source documents that rule by naming what it must not do). **UNBUILT: authored on Linux with no Xcode and no Swift toolchain, so the harness has never run.**

- **A connected folder's images could not be read at all, and iCloud was never why (prd §604, 2026-09-04).** `-filesHealProbe YES` reports the pass (`thumbed`/`ocred`/`pending`, then per row its OCR length, whether it has pixels, and its current title). **A file in a picked folder is readable ONLY inside an active `startAccessingSecurityScopedResource` window on that folder, and outside one the refusal is indistinguishable from "the bytes are not here yet"** — `CGImageSourceCreateWithURL` returns nil either way, so `ocrRead` reports `attempted == false`, `ocrAt` is correctly left nil, and the same file is re-read and re-fails on every foreground pass forever. One cause, all three symptoms: no thumbnail, so no tile (the §283 grid admits a row only once it has pixels); no OCR; and no retitle, so every row keeps its raw file name. **A refactor did it and it stood for five weeks** — the scope used to be opened at the top of `FilesIngest.heal` and cover the read loop, and on 2026-07-29 the walk moved into a detached task and took the scope with it; the §283 grid shipped four days later on top of that, so a folder's images have arguably never healed on a real device. **The asymmetry is the tell and it points the wrong way**: a VIDEO still tiled (`ImportMedia.posterFrame` opens the scope itself) and a text file still previewed (`preview(of:)` runs inside `refresh`'s scoped task), so the only read that broke was the only one with no scope of its own — and **no check here could see it, because on the simulator a picked folder is usually in-sandbox, `startAccessingSecurityScopedResource` returns false, and the reads succeed anyway.** The 2026-09-03 fix read it as iCloud eviction and was wrong; that `startDownloadingUbiquitousItem` request is still made and still right for a genuinely evicted file, but it was never the cause — the generalisable half being that **a read refused for permission and a read starved of bytes look identical at the call site**, so rule out the one you control first. **The ruling: the scope belongs to the READ**, never to whichever caller happens to enclose it — `thumbnail` and `ocrRead` take the folder and open their own window, which is `posterFrame`'s contract and exactly why that one survived the refactor that broke these two. Guarded by `scripts/files-scope-selftest.sh` (in `verify.sh`), which reads ONE FUNCTION'S BODY rather than the file — this file opens a scope in three other places, so a file-level grep passes vacuously and is precisely the check that would have called the broken tree clean; 4 mutations, each a single-line deletion of the thing a check names. **UNPROVEN on a device**: the closure is demonstrable in the source and the symptoms match it exactly, but no read has been watched succeeding on a real picked folder. The tell will be titles — a CleanShot name is in `isMachineGeneratedName`, so a healed row stops naming the file and starts saying what the picture says. **§1376 (2026-10-17, the third report):** the scope was not enough. Every read now goes through `NSFileCoordinator` (`coordinatedRead`, 15s cap), which is what makes iCloud bring a file to the phone; a heal pass reads six not-yet-downloaded files at most and starts nothing after 60s; and the open sheet reads its own picture (`FilesIngest.fillPicture`, `PhotoWell(readsFolder: true)`).
