- `-theme.light 0|1` — AppStorage theme override; always pass explicitly for light/dark screenshots (the sim's stored value sticks). Note the **crown pour is OFF by default since 2026-08-04** (prd §204 amendment): `ThemeStore.bleeds` gained a sixth option, `Ink`, and it leads the list so it's what an unset `theme.bleed` resolves to. Ink does NOT pour black — `pours == false` takes `MainSurface.crownPour`'s dose to zero, because black at the light theme's own 0.16 top stop is a grey stain across the top of every screen rather than an absence. A SCOPED wallet still re-tints the crown (`chrome.pourHue` wins first): that pour is information, the same distinction §297 drew when it drained the dose on a source room without dropping the hue. So a screenshot expecting the blue pour needs the colour picked explicitly now.

- `-trayGlass material` — force the pre-26 material RECIPE for the sources tray on an iOS 26 build (`Design/DSTray.swift`, `DSTrayGlass`). DEBUG only; anything else (or absent) draws the system's real Liquid Glass, `glassEffect(.clear)`. **The two are a PAIR, not a migration** — the app deploys to **iOS 18** and `glassEffect` is 26+, so the recipe is what most devices draw and cannot be deleted. It exists because the choice between them is undecidable from this host: no simulator renders Liquid Glass the way hardware does, and the question that separates them — do 12pt `textSecondary` chip names survive over an edge-to-edge picture feed, which is exactly the contrast `.clear` withholds by design — is one only a device can answer. One build, both treatments, no re-ship to compare. Standing lesson from the walk it ended: **fading a material does not make it transparent, it makes it weak** — `.opacity()` on `.ultraThinMaterial` (0.82 → 0.72 → 0.62 → 0.55 → 0.45 across two sessions) spends the frosting that buys legibility to buy back clarity, while the system has had an actual transparent variant the whole time.

Reachable from three doors: the greeting's own CTA (`-howItWorksCTA`, above), the fork's fourth card (`-startPick demo`, above), and a Settings row ("See the demo") gated on a DEMO-CLEAN corpus (`AccountScreen.demoReentryAvailable` — every connected bridge must be a demo seat by name, and no wallet watched; the gate exists because `DemoMode.exit` FORGETS PostHog metrics named `signed_up`/`answer_asked` by name, which would destroy a REAL PostHog connection's readings on a lived-in install). Exit always lands on the fork (`HomeRoute.startHere`), never the catalog and never the empty feed — §217's own ruling that the catalog is "a wall you have to survey" against the fork's "a fork you answer in a second" only got stronger as the catalog passed 60 seats, and someone who's just watched a furnished app fill has exactly the question the fork asks. **THE DEMO REACHES NOTHING** — `BridgeRefresh.refreshAllConnected` returns instantly while `DemoMode.isActive` (a real sweep would read the seeded-but-fake wallet address and write a value sample of ZERO over the seeded curve, which renders as a balance that fell off a cliff — the exact "flat curve reads as went to zero" failure `agent-panel-selftest` exists to prevent, arriving by a route that self-test can't see) and `Notifications.submit` returns `[]` in demo mode unless `dryRun` (a lock-screen alarm about a fake £240 dispute would burn the one-and-only authorization prompt on someone who hasn't decided whether to keep the app). **Agent MEMORY is seeded too, not just the corpus** (2026-08-07) — `BriefLedger.seedDemo` plants ~6 prior-window entries (real symbol "ETH", real tags "Release"/"Alert" the seeded corpus actually carries) so the Today brief's streak lede fires on the FIRST open, `AskMemory.seedDemo` primes a stale tile (proving live demotion) and an already-past-mint-threshold ask (proving the "keep it?" upgrade), `AppVisit.seedDemo` fakes a 3h-ago close stamp so "While I was away?" has something to answer immediately. All of it unwinds symmetrically in `exit` — `BriefLedger.restoreDemoCheckpoint` restores to a snapshot taken BEFORE `begin` touched anything (removing both the seeded entries and any REAL entry recorded live during the session, since a Today-brief composed over the demo corpus describes a corpus that's about to stop existing). **Freshness re-stamp** (`DemoMode.restampIfStale`, called on every activation): a demo left alive past ~20h shifts every demo-owned row's dates forward by WHOLE DAYS (never touching time-of-day, so the day-dial's hour spread survives; every row shifts the SAME amount, so a heatmap's relative shape survives even as absolute weekdays drift) — plus the wallet balance curve and the `BriefLedger` seeded windows, or the ledger's streak reads as broken the moment real time outran the seeded dates. **Two concurrent-call races, found on the sim, not by reading (2026-08-07).** `pourIfNeeded`/`restampIfStale` are `async` and suspend mid-run (the chunked write loop's own yield), and both gained a SECOND call site the same day (`RootShell.handleActivation`'s unconditional resume-call, `-demoEnter`'s probe hook) — `pendingKey` alone doesn't serialize two callers racing each other, only tells each "something is pending". First symptom: a fresh `-demoEnter` launch poured **370 rows, then 406 more, on the SAME launch** — the second caller's "landed" snapshot was taken mid-way through the first caller's still-running insert loop, so it re-landed everything the first hadn't gotten to yet. Fixed with an in-memory `pouring` flag guarding entry (`guard !pouring else { return }`, `defer { pouring = false }`) — NOT the persisted `pendingKey`, which exists for CROSS-launch resume and must stay set until the pour genuinely finishes. That fix immediately surfaced the second race: a caller whose `pourIfNeeded` got blocked by the new guard returned INSTANTLY, and `handleActivation`'s sequential `await pourIfNeeded(); await restampIfStale()` cannot tell "blocked by someone else" apart from "nothing was pending, safe to proceed" — so it walked straight into a restamp against a corpus the OTHER caller was still actively pouring into, logging `re-stamped 24 rows` while `poured 406 rows` was still four seconds from finishing. `restampIfStale` now also guards on `!pouring` (any in-flight pour, not just its own `restamping` flag), which is the actual fix — a caller blocked from pouring must also be blocked from restamping, since both read state the other write is still producing. Verified via `-corpusDupeProbe YES` against the fully-landed corpus post-fix: **414 refs, 414 distinct, 0 duplicated.** **Exit fades before it deletes** (`ShellChrome.demoLeaving`, one opacity on one container, ~420ms) rather than animating rows out individually — animating the removal of 300+ `Thing`s through a live `@Query` feed is precisely the six-corollary SwiftData liveness crash class this file documents at length; - **The phone's own perf numbers, on the phone (prd §623, 2026-09-06, `Model/PerfReadings.swift`).** `-perfReadingsProbe YES` prints this device's perf readings — one `perfReadings|` line per line the Diagnostics screen draws, through the SAME `PerfReadings.lines`, so the probe is evidence about the screen rather than a second opinion beside it (the `NetworkLedger.resolvedService` lesson). Five spans: open → first screen, the foreground sweep, ask → first paint, ask → settled, and the worst main-thread stall a sweep produced. **The readings PERSIST across launches**, so the launch that reads something is the one AFTER a launch that swept and asked; `-perfForget YES` empties them first (declared before the probe, for the clear-then-read order). `-perfMeasure YES|NO` flips the "Measure stalls" switch the screen owns — the same two defaults keys (`launchTimer`, `sweepTimer`) the launch arguments set, persisted instead of per-launch — so a headless run can prove one toggle reaches both gates. **It measures nothing**: every reading is handed in by an instrument that already fires once per user event (`AppSignposts` at each MetricKit `.end`, `SweepClock.report`), so the number on the screen and the number in Apple's daily histogram are one stopwatch. **Unlike `-metricsProbe`, this is NOT empty on the simulator** — the readings are the app's own, so a sim run does exercise the whole path; what a sim cannot tell you is what the numbers are on a phone, which is the entire point of the feature.

- **`-sourceRoomLightColumns YES|NO` — the source room's projection, forced (prd §623, 2026-09-06, DEBUG only).** `FeedScreen.sourceRoomLightColumns` gates `propertiesToFetch` on `#available(iOS 26.0, *)`: the combination of a partial fetch and a `#Predicate` on a live query returns rows the predicate never selected on iOS 18.6 (§592) and is correct on iOS 26 — same binary. This override forces it either way regardless of OS, and is how the 18.6 arm is driven; `#if DEBUG`, so no shipped binary carries a knob that can turn the defect back on. Pair it with the `roomNet|` line the room's own safety net logs in DEBUG (`source`, what the LIVE query returned, and whether the projection was on) — a plain `context.fetch` cannot see this defect, which is why three attempts to reproduce it against a plain fetch found nothing. **A launch argument lands as a STRING**: the first run of this read it `as? Bool`, got nil, and measured the OS gate twice while reporting `lightColumns=off` in both arms.
