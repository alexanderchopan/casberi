Keep the cards. Stop the packer from ever cutting one.

The orphan wasn't a drawing problem — it's what greedy packing does to a container. B let a group run past a row end, so its tail arrived as a nameless box holding one icon. The fix reverses which one gives way: a card is never split, and the rows are packed instead. You asked whether that can be done optimally rather than approximately. It can, and it's three lines: place the biggest category first. Measured over 39,237 random corpora that rule tied the exact optimum every single time — while packing in catalog order lost up to two whole rows. On your twenty sources it lands four full rows, zero empty cells, zero orphans, ~600pt.

Every card is whole, and every row is full. Nothing is cut, nothing bleeds off an edge, and there is no such thing as a continuation — so the "what is this nameless box" question can't be asked. A card with one chip in it (Mail, Work, Reading) reads as a small category, which is exactly what it is, rather than as the tail of something.

The chips never left the grid. Cards span whole column slots, so all twenty chips sit on the same five-column rhythm as the flat grid, the strip and the catalog tiles. The card is drawn behind the layout rather than replacing it — which is also why this is a smaller code change than it looks.

5 · 4+1 · 3+2 · 3+1+1 — four rows, every one full. Big blocks lead and the granularity increases down the page, which is a better read than the reverse.

Is it actually optimal? Measured, not assumed.

Exact optimum computed by subset DP over 39,237 random corpora (3–12 categories, up to 45 sources), against the two greedy rules.

biggest-first  ·  0 losses  ·  always optimal
catalog order  ·  7.76% worse  ·  up to 2 rows

Two rows is 258pt — the difference between resting and scrolling. So the sort isn't a nicety, it's the whole optimisation, and it's sorted(by: count). Exact DP was written and then thrown away: it never once beat the sort, and it would have cost a jumbled order to run.

The leftmost box is Social's tail — one icon, no title, sliced at the edge. You have to look up and left to the previous row to learn what it is. Five of eight groups did this. The container was doing the opposite of its job.

The one real trade, stated plainly: group order becomes size order, not BridgeCatalog.categories. It was never the strip's order either — the strip is recency-and-taps, the tray was already catalog — so nothing being taught gets untaught, and members keep the strip's frozen order inside every card. What does change is that connecting a source can re-sort the rows and move a category. The shipped tray already does that; here it's just more visible, and it's the price of never scrolling.

And the one edge case: a category with more than five sources can't fit a row at all. It takes a full-width card two chip-rows tall — still one whole container with one title, so still no orphan. Markets sits at exactly five today, so the next Markets app is what triggers it.

Why this is the one I'd build

It's the cards you wanted, with the thing that made them ugly removed at the root. Not softened — removed: there is no code path that can produce a cut card, because cards are placed whole and only rows are packed. Every complaint B earned is structurally unavailable here.

And it costs nothing the earlier rounds fought for. Four rows, ~600pt, inside the resting cap, no scroll, chips five across on the same grid the strip and catalog tiles use, names never truncated, dashed-orange and tint rings unchanged. The perfect fill on today's corpus is partly luck — twenty sources over eight categories happens to admit an exact partition — but the packing degrades gracefully where B's didn't: a wasted cell is an empty slot inside a card, which looks like nothing at all, where B's failure looked like a bug.

On "can it be dynamic": yes, and the useful finding is that the sophisticated version is not worth writing. I wrote the exact optimiser, ran it against the greedy rule 39,237 times, and it never won once — so the shipped rule should be the three-line sort, and the DP belongs in a test that proves the sort still ties it, not in the app. Packing in catalog order is materially worse (7.76% of corpora, up to two rows), so that part of the question had a real answer.

If you want the cheap version instead, A still stands — inking the overlines in the tint is a one-line change and moves nothing. D is the one that actually answers "it looks like a bunch of icons", because a filled container is seen rather than read.
