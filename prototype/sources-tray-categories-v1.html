Your sources, grouped the way the catalog groups them

Three ways to put category structure into the sources tray, drawn against your actual twenty sources and the real mapping in BridgeCatalog.categories. Each one trades against the same thing: the tray's order is the strip's frozen order today, and position is half a chip's identity when the chip has no label. Grouping re-sorts. What differs is how much, and what it costs in height.

The category name takes a cell. One continuous five-across grid, no headers, no second rhythm — the name simply occupies a slot and everything after it belongs to it until the next name. Nine cells' worth of structure instead of eight full rows, so it lands within a whisker of today's height.

The honest cost is visible in rows 5 and 6: Polymarket is orphaned from Markets across a row break, and the last row carries three groups at once. Grouping is real but soft — you read it as a marker passed, not a block entered. A marker never sits in the last column (it would strand its members entirely), which is the one layout rule this needs.

Everything keeps today's grid, untouched

Nothing moves until you ask. "Everything" is the default and is byte-for-byte today's tray — the frozen order, all twenty, one glance, no scroll. The pills are a filter over that one grid, so category structure is available without ever being imposed.

It's the only version that fits the existing 620pt cap, and the only one that costs a tap. The tray keeps a fixed height across pills rather than resizing per category — a tray that breathed as you tapped would jitter under your thumb. Note this is a new control, which §269 was wary of for the feed's tag filter; the pills also collapse eight categories to six by folding the singletons into "Me".

Three things to rule on before any of this gets built

Which order do the categories go in? All three use BridgeCatalog.categories' own order — Wallet, Social, Mail, Media, Markets, Life, Work, Reading — so the tray reads like the catalog you already know. The alternative is first-appearance order, which would keep the tray's own top-left the same chip it is today. They disagree after the first entry.

Does grouping fight the freeze? The tray's doc says a grid that re-sorted itself would teach the opposite of what the frozen order protects. A and B both re-sort and answer it by keeping the strip order inside each group; C answers it by not re-sorting at all unless asked.

A rail was tried and dropped. Category name in a left column with four cells beside it reads beautifully and computes to ~1,060pt — within 15% of the bands version, because a one-app category still claims a whole row. It gives up the five-across rhythm and buys almost nothing back, so it isn't pitched here.

Icons are simplified stand-ins; the build uses the same BridgeIcon marks the strip does, and every ring reads exactly as it does today — solid tint is where you are, dashed orange is a connection that needs you.
