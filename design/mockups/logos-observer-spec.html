Logos Observer v2: a read-only window onto your node

Frozen for implementationLogos × Casberi3 October 2026Contract v2

Casberi is an iOS and Mac app that shows a person their own Logos node: whether it's in sync, its peers, whether it's mining, and what rewards are waiting. The Observer runs next to the node and answers a paired device's reads, and nothing else.

In short: TLS handles the secure channel, an HMAC identifies the paired device, scopes define what it may read, and the Observer stays a strict read-only boundary around the node API.

Requirements

Must marks a requirement. Should marks a recommendation.

  1. The raw node API stays on 127.0.0.1:8080 and is never exposed to the LAN.
  2. The Observer must serve only the routes in Routes. Nothing proxies an arbitrary path, and every other method or path returns 404.
  3. All traffic must use TLS 1.3 to an Observer identity the device pinned at pairing.
  4. Every request after pairing must carry an HMAC signature with a timestamp and a fresh nonce. Nonces are kept across restarts.
  5. A device can read only the scopes it was granted.
  6. The person must be able to see and revoke every paired device from the Observer.

Scopes

Read scopes (v2)

ScopeNode routes it coversCasberi requests
node.status.readGET /cryptarchia/info: phase, height, tipYes

mining.status.readGET /pow/statusYes
rewards.status.readGET /pow/rewards/claimable, GET /leader/claim/vouchers?tip=Yes
blend.status.readReserved until Logos names the underlying node dataNo. Reserved.

Control scopes (reserved, not in v2)

mining.control, rewards.claim, node.control

  • Control is a separate privilege class. It needs its own explicit consent and has its own routes.
  • The Observer must not grant read and control scopes in the same pairing. A compromised read-only dashboard can't inherit control.
  • Casberi will never request a control scope.

  "observed_at": "2026-10-03T14:02:11Z",

  "network": { "peers": 12 },
  "mining":  { "is_mining": true, "rewards_enabled": true, "auto_claim": false },
  "rewards": { "claimable_tickets": 3, "slots_until_expiry": 412,
               "vouchers": 2, "total_claimable": "15.000000" }
}
  • A section that isn't granted is left out. A section whose read failed is null. A failed read is never 0, so the phone can say "unknown" instead of "not mining".
  • A node that's down is still a 200, in exactly the shape below. That tells "your node stopped" apart from "the Observer is unreachable".
  • Amounts are decimal strings.
  • Voucher commitments and nullifiers never leave the Observer. Only the count does.
  • The Observer should cache a reading for 10 seconds, so two devices don't double the load on the node.

Node down

{
  "v": 2,
  "observed_at": "2026-10-03T14:02:11Z",
  "node":    { "reachable": false, "phase": null, "height": null, "tip": null },
  "network": null,
  "mining":  null,
  "rewards": null
}

Every granted section is present. The node section keeps its keys with null values, and the other sections are null. tip is the node's full block id, or null. It's never abbreviated on the wire.

Transport

  • TLS 1.3 only, with a self-signed ECDSA P-256 certificate the Observer generates on first run and keeps. Apple's TLS stack doesn't accept Ed25519 server certificates, so Ed25519 would make the Observer unreachable from iOS.
  • The pin is the SHA-256 of the DER-encoded SubjectPublicKeyInfo, written sha256/<base64url>. It survives a certificate renewal that keeps the key. A new key means every device pairs again.
  • The device accepts no certificate whose key doesn't match the pin. No CA is involved.
  • The Observer should advertise over Bonjour as _logos-observer._tcp, so a device can find it after its address changes. The pin makes that safe.
  • The default port is 8081, and it is configurable.

Pairing

1. The QR

logos-observer://pair?v=2
  &exp=1791068753
  &h=192.168.1.20:8081
  &b=Logos%20Observer._logos-observer._tcp
  &pin=sha256/<base64url>
  &s=<base64url 32-byte bootstrap secret>
  &n=<Observer display name>
  &sc=node.status.read,network.status.read,mining.status.read,rewards.status.read
  • Valid for 5 minutes and one successful pairing. Voided after 5 failed attempts.
  • Shown only on the Observer's own screen or terminal, never served over the network.
  • Keep it under about 300 characters, so it scans from across a desk.
  • The device's HMAC key is never in the QR. A photo of a used QR is worth nothing.

2. Consent, on the device

Before sending anything, Casberi shows:

  • the Observer's name and address
  • each offered scope, in plain words
  • Approve and Cancel

The person can untick a scope. The approved subset goes in the activation request.

3. Activation

POST /v2/pair
{ "secret": "<from QR>", "device_name": "Alex's iPhone",
  "scopes": ["node.status.read", "network.status.read",
             "mining.status.read", "rewards.status.read"] }

200
{ "device_id": "d_7Kq2…", "hmac_key": "<base64url 32 bytes>",
  "granted_scopes": ["node.status.read", "network.status.read",
                     "mining.status.read", "rewards.status.read"] }
  • The device treats granted_scopes as the truth, and Casberi draws only those sections.
  • Casberi stores hmac_key in the iOS Keychain as a device-only item. It doesn't sync to iCloud or restore to another phone.
  • The Observer must then show "Paired: device name". Whoever scans first gets the pairing, and this is how the person notices if it wasn't them.

Signed requests

GET /v2/status
X-Observer-Device:    d_7Kq2…
X-Observer-Timestamp: 1791068453
X-Observer-Nonce:     <base64url 16 random bytes>
X-Observer-Signature: <base64url HMAC-SHA256(hmac_key, canonical)>

canonical =
  "LOGOS-OBSERVER-V2" \n
  METHOD \n
  request-target \n
  timestamp \n
  nonce \n
  device_id \n
  hex(SHA-256(body))       // empty body: SHA-256 of ""
  • request-target is the exact bytes sent on the request line, in origin form: the path, then ? and the query only if there is one. Query order and percent-encoding are kept as sent, with no normalisation. There's no trailing ? when the query is empty, and never a fragment.
  • Allowed clock skew: ±120 seconds. Nonces are kept for 5 minutes and survive a restart.
  • The Observer checks the device, then the time, then the signature, then the scope, then consumes the nonce, and only then reads the node.

Errors

401 replayNonce already usedRetries once with a new nonce
403 scopeScope not grantedStops asking for that section

The body is {"error": "<code>"}. Only revoked ever clears a credential.

Managing devices

For each paired device, the Observer shows:

  • its name and when it paired
  • its granted scopes
  • when it was last seen, and from which address
  • a Revoke button

Credentials don't expire while they're in use. A device unused for 90 days should be revoked.

What the network can still see

Someone on the LAN sees the Observer's address and port, when requests happen, and how big they are. Paths, headers and responses are inside TLS. Casberi's setup copy will say the same: what your node reports is private, but your network can see that you're reaching it.

Basecamp's module capability policy is fail-open. If the Observer runs as a module, its own allowlist is the only boundary. v2 calls the node's HTTP API and no other module.

Migration

  1. Logos keeps v1 running while v2 is built.
  2. Logos adds the TLS identity, the v2 QR with its pin, plain HTTPS JSON in place of v1's encrypted envelope, device name and last seen, and machine-readable scopes. HMAC and persistent replay protection stay.
  3. Casberi builds the pairing consent screen and the v2 client. Casberi builds against v2 only, never v1.
  4. Logos runs v1's adversarial and replay tests against v2.
  5. Casberi pairs with a real node.
  6. v1 retires once the two interoperate.

What Casberi needs from Logos to start

  • An HMAC test vector: key, request, canonical string, expected signature.
  • A pin test vector: a sample certificate and its sha256/… pin.
  • A sample QR string.
  • The reference Observer, runnable on a Mac, so Casberi's tests can pair against it.
