# Casberi

Native iOS app — a personal corpus of "things" (links, screenshots, events, chats, voice notes, agent outputs) with on-device generative UI synthesis. Solo project, pre-App Store (Developer Program enrollment active; shipping via TestFlight, App Store v1 not yet submitted).

**How this file is organised.** It is a RULE SHEET, loaded into every session — rules,
build commands, gotchas, and a one-line index of every DEBUG hook. The long-form record
of how each thing was built and what it cost lives in `docs/`:
`docs/verify.md` (the verification pipeline), `docs/hooks/*.md` (per-area feature and
probe entries, verbatim), `docs/prd.md` (the append-only ruling ledger, reached by `§N`).
Every index line below names the file to open. **Keep this file under 100KB** —
`verify.sh` fails the pass above that; new long-form entries go to `docs/`, not here.

## Repository & working directory (RULE)

- **The canonical working copy is `~/Developer/casberi` — NOT iCloud Drive.** Always work here. The old iCloud copy (`.../myStuff/product/casberi`) is deprecated; do not edit it.
- Backed by a **PUBLIC** GitHub remote `origin` → https://github.com/alexanderchopan/casberi (public by the user's choice, confirmed 2026-08-02 — this doc said "private" until then, which was wrong). Two things follow, both load-bearing: **every commit is world-readable the moment it lands** (the auto-push below is immediate), so nothing secret may EVER be committed — real keys live in the macOS login Keychain via `scripts/dev-keys.sh`, and the only credentials in-tree are ones that are safe in public by design (the Reown/WalletConnect project id, a Dropbox app key — both public identifiers, not secrets); and Actions minutes/storage are FREE for public repos, so nothing here counts against the account's Actions allowance. A `post-commit` hook auto-pushes to `origin` in the background on every commit (off-site backup) — so `git commit` alone keeps the backup current; a manual `git push` is only needed if a push failed while offline (see `.git/last-autopush.log`). Commit workflow is unchanged otherwise: solo, straight to `main`, no branches/PRs required. Note: committing/pushing to `main` is NOT a release — releasing is the separate archive+upload step (`scripts/testflight.sh`).

## Building (critical)

From the canonical `~/Developer/casberi` copy, a plain build codesigns cleanly — no workaround needed:

```sh
xcodebuild -project Casberi/Casberi.xcodeproj -scheme Casberi \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
```

Or just run `scripts/verify.sh` (build + install + screen sweep + answer probe).

**The pass, in the rules a session needs before opening anything.** Full record:
`docs/verify.md`.

- **Run `scripts/verify.sh`, not the audits you happen to remember.** That is mechanical,
  not moral: a build shipped an undisclosed host because two audits were run by hand and
  green, and the third was never invoked.
- It **compiles Mac Catalyst and hard-fails** (step 1b), and **launches `verify-mac.sh` in
  parallel and gates on it** — so one green means both platforms, and a Catalyst break is
  reported where the Mac leg is waited on, at the end.
- Audits and self-tests are **discovered (`scripts/*-audit.{py,sh}`) or hand-listed and
  proven complete**; every check must have a `--self-test`, because a check that cannot
  demonstrate it catches anything certifies nothing.
- The ~93 pure-logic harnesses run **concurrently, longest-first, through a skip cache**
  keyed on the harness plus every input it names. A failing harness is never stamped.
- The **nightly ledger is read back and REPORTED, never gated on** — its verdict describes
  a different commit, and staleness is reported apart from failure.
- `scripts/live-integrations.sh` stays **separate and warn-only** (keyless third-party
  liveness, always `exit 0`). Do not fold it in and do not add a keyed check to it.
- Knobs: `--build-only`, `LAUNCH_CYCLES=0`, `SKIP_CATALYST=1`, `SKIP_MAC=1`, `SKIP_LIVE=1`,
  `SKIP_LOGIC=1`, `VERIFY_NO_CACHE=1`.
- **Read `$OUT/step-times.tsv` (slowest ten, printed by the EXIT trap) before aiming any
  work at this suite.** Three separate passes have found that "verifying is slow" was not
  the standard cost of good tests.

## Simulator gotchas

- Typing via computer-use `type` triggers the macOS accent-picker. Instead: `printf "text" | xcrun simctl pbcopy booted`, then cmd+a, Delete, cmd+v.
- Sim switches don't respond to computer-use clicks — drag across the knob.
- Dynamic Type: `xcrun simctl ui booted content_size` (underscore).
- Launch args do NOT trigger `onOpenURL` — use the `-deeplink` hook below, or `xcrun simctl openurl booted casberi://...`.
- Computer-use approval is blocked in scheduled/non-interactive runs — drive the app via launch-arg hooks + `simctl` there.
- Installing for probes: pick the NEWEST DerivedData (`ls -dt ~/Library/Developer/Xcode/DerivedData/Casberi-*` — plain `ls -d` is alphabetical and served a day-old binary for 30 minutes on 2026-07-14). `runAll` NSLogs `probeArgs:` with the launch args it saw — if that line is missing or stale, you're running the wrong binary.
- **`booted` is ambiguous with two simulators up** (2026-07-21): a second Claude session boots its own device, and from that moment every `xcrun simctl … booted` (install, launch, screenshot) may resolve to THEIR device — as can computer-use/simulator-MCP taps, which pick the frontmost. The symptom reads as a stale build: your new strings are in the binary, the screen shows the old UI, and the app randomly leaves the foreground (they terminated it). Pin the udid on every call (`xcrun simctl list devices booted` to get it, then `xcrun simctl launch <udid> …` and the simulator tool's own `udid:` argument) the moment a second device appears.
- **Verify the INSTALLED binary, not just the newest one** (2026-07-16): `ls -dt` globs across EVERY `Casberi-*` DerivedData dir, so when a second Claude session is building concurrently it can serve you THEIR app — which silently lacks your probe hooks. The symptom is maddening: `probeArgs:` logs your args correctly, and the hooks just never fire (they're absent from the binary, so `string(forKey:)` finds nothing to match). Three runs were misdiagnosed as rate limits and regressions before this was spotted. Check the bundle you actually installed: `strings "$(xcrun simctl get_app_container booted com.casberi.app app)/Casberi" | grep -c '^myHookKey$'` — 1 means it's really there. Concurrent sessions also share one build DB (`database is locked` → just retry until it clears).
- On a fresh sim install the demo seeds re-ask Photos/Calendar/Health permission at launch, and the queued sheets block everything (probes still run, but the UI is unusable and Health's ask stalls its probe). Pre-grant what simctl can (`xcrun simctl privacy booted grant photos com.casberi.app` — AFTER install; uninstall wipes grants) and tap the Health sheet once via computer-use; grants then persist for every later headless run.

## SwiftUI/UIKit gotchas already paid for

- **A quick action is REGISTERED on the app delegate and DELIVERED to the scene delegate (prd §377, 2026-08-14).** `application(_:performActionFor:completionHandler:)` is never called in a scene-based app — which every SwiftUI `App` is; the action goes to `windowScene(_:performActionFor:)`, and a COLD launch arrives as `UIScene.ConnectionOptions.shortcutItem`. Shipped broken for eleven days and looked healthy, because registering and handling are different delegates. `Shell/QuickActions.swift` owns both doors; the durable flag and the `QuickAction.received` notification are both needed, and neither is reachable by any harness here. **STANDING RULE: for any UIKit hook concerning the SCENE — quick actions, state restoration, cold-launch URL/activity continuation — check which delegate the current lifecycle delivers it to before writing the handler; getting it wrong fails silently, and silent here reads as "the app opened normally".** → docs/prd.md §377
- A background layer BEHIND a NavigationStack never shows through (opaque UIKit backing). Page backgrounds paint INSIDE each screen: `.dsPageBackground()` on the scroll container; List also needs `.scrollContentBackground(.hidden)`.
- **A feed ROW never carries a presentation of its own — one screen, one `.sheet` (third time paid for, 2026-07-28).** `FeedScreen` presents through exactly ONE `.sheet(item: $feedSheet)` (`FeedSheetRoute`) because five sibling `.sheet` modifiers on the screen made the first tap silently self-dismiss. The same rule reaches DOWN the tree: a `.sheet` attached to a view INSIDE a `List` row resolves to the same presenting UIViewController, so the row's tap starts the thing sheet and the row's own sheet modifier tears it back down mid-transition — the sheet rises PART WAY and closes again. Symptom, user-reported: "opening fc feed items doesn't work, it opens half way and closes". Cause: the 2026-07-27 social pass moved `ReplyingToRow` and `SocialQuoteCard` — both `Button` + `.sheet(isPresented:)`, correct inside `ThingSheetView`, which is itself a presented sheet — into `PostCard`/`SocialThreadCard`, i.e. into feed rows. Farcaster wore it worst because nearly every cast it lands has a parent or a quote (channel casts, mentions and likes are mostly replies), so nearly every fc row grew the extra sheet. THE RULE: a row is a read with ONE gesture (tap → the thing sheet, ruling 2026-07-16); anything walkable inside it renders as context (`allowsHitTesting(false)`), and the walk lives in the sheet, which routes through its own single presentation (`ThingSheetView.walkingTo`). A component used in BOTH places takes a flag (`SocialQuoteCard.walkable`) rather than presenting unconditionally.
- **Decorative motion during a refresh must be CoreAnimation, not SwiftUI** (2026-07-28, user: "the rain pour always lags on pages"). SwiftUI interpolates `.offset`/`.opacity` per frame on the MAIN actor — and every ingest in this app is `@MainActor` (inserts/deletes on the main context, each re-emitting the feed's `@Query`), so a pull-to-refresh delight animates in exactly the window where the main thread is least able to draw it. It stuttered by construction, every time. `Design/TileRain.swift` now deals `CALayer` tiles with a `CAAnimationGroup` (position + opacity, `beginTime` for the stagger, `.backwards` fill), which the render server drives out of process — smooth while the main thread is blocked solid. Corollary from the same fix: ONE gesture deals ONE shower. `refreshFeed()` bumped `chrome.refreshPulse` a second time a few ms after `.refreshable` already had, re-dealing the in-flight drops over the same identities.
- `UIGraphicsImageRenderer` defaults to device scale (3×) — pin `format.scale = 1` for downscale renders.
- A bare `Image().resizable().scaledToFill()` in a ZStack expands the ZStack to image size — pin in GeometryReader + `.clipped()`.
- A child `.gesture(DragGesture)` beats ScrollView vertical scroll entirely on device — use native `swipeActions`, never custom swipe DragGestures in scroll content.
- Silent `try?` on EventKit (and similar) writes swallows denials — surface outcomes via `ShellChrome.flash()`.
- A SwiftData `#Predicate<Thing> { $0.tags.contains(x) }` (`tags` is a transformable `[String]` attribute) COMPILES clean but crashes at RUNTIME — EXC_BAD_ACCESS/SIGSEGV inside CoreData's `_NSCoreDataStringSearch` mid-SQLite-fetch (found 2026-07-21 scoping `ProjectDetailScreen`'s `@Query` to a project's tag as a perf win; reproduced by opening a project, confirmed via crash report, reverted). Plain string-equality predicates (`$0.source == source`) are fine and already used throughout `Model/IngestSupport.swift` — the crash is specific to `.contains` on an array-typed attribute, which SwiftData can't safely push down to SQL here. Filter tag membership in Swift AFTER an unscoped fetch instead; don't reintroduce a tags-array predicate without verifying against a real on-device fetch first.
- **Never key a `ForEach` on a persistent `@Model` property from a DERIVED array — the perpetual "crashes on different screens after an update/first sync" class.** Reading any stored property of a deleted/invalidated `Thing` traps inside SwiftData. A `ForEach` directly over a `@Query` is safe; one over a `.filter`/`.map`/`@State`-held array is NOT. **Six corollaries, each a shipped crash (builds 142, 150, 176, 177, 188, 250) — read them before touching a view or an `async` func that holds a `[Thing]`; the last two leave the view layer entirely** → docs/liveness.md · enforced by scripts/swiftdata-liveness-audit.py
- `navigationDestination(item:)` gates on VALUE EQUALITY, and SwiftUI writes its own `nil` back into that binding when the pushed screen dismisses — the catalogue-door mint-stamp saga (user: "I have to click it a few times", 2026-07-22). SUPERSEDED 2026-07-22: `HomeRoute` no longer uses `navigationDestination(item:)` at all. Multiple sibling item bindings anchored to the same `NavigationStack` root turned out not to nest — pushing a bridge setup screen (`bridgePush`) while the Apps door (`push`) was open silently dropped Apps out of the real stack, so the native back chevron on a connect screen (Coinbase, Kalshi, …) landed on the Feed instead of the Apps catalog it was opened from. Appending is never gated by value equality, so the old mint-stamp workaround (`HomeRoute.Push`, a struct pairing a door with a mint stamp) is gone too — every `path.append` is a real array mutation SwiftUI has never seen before, and an early push sitting in `path` before the stack mounts renders correctly on the first frame (read directly, not edge-triggered) with no re-landing dance. Corollary: a plain (valueless) `NavigationLink { Destination() }` pushes a frame the bound `path` array doesn't track — appending to `path` while one is on top drops it (the stack resyncs to `path`'s own count). Any screen that might later have something pushed onto it via `HomeRoute` needs its OWN entry pushed through `route.path` (`NavigationLink(value:)` against a `HomeRoute.Node` case), not a plain NavigationLink — see `AppsScreen.swift`'s `catalogTap`. - **EVERY POUR IS INK — `DS.pourInk`, one token, no exceptions (prd §524, 2026-08-29).** A card, a sheet head or a page gets a top the same way everywhere: `pourInk` → clear over 150pt (a page's own washes run longer), alpha baked into the adaptive colour so no view reads `colorScheme` for it. **`dsReceiptPaper` does not TAKE a colour** — the `Color?` whose nil meant "no pour" is gone, because a neutral makes no claim to opt out of and a paper without a top is the "jumble of text" §495 exists to fix. - Honesty rule: no dead controls, no fake status. Three corollaries the 2026-07-16 audit paid for (prd §83): a hand-rolled button that paints its own background MUST swap that background when disabled — `.disabled` dims a plain-style button's label, not your background, so it reads live while inert (prefer `BridgeFieldRow`); never quote a price off a stale last trade — quote the live book's own bracket midpoint, or show nothing (an empty bid-0/ask-1 book is the one bracket that says nothing; its midpoint would invent a 50% coin flip), and read both sides of a delta the same way; and a change that rounds to zero has no direction — no sign, no green/red (`TokenChartStyle.isFlat` / `accent(change:)`). - **THE MAC TAKES ITS OWN POINT SCALE — `DSTextStyle.macScale = 0.88`, one lever, no per-rung tuning (prd §631, 2026-09-06).** `TARGETED_DEVICE_FAMILY` includes family 6, so a point here is an AppKit point at 1:1 and the app's 17pt reading band rendered at a true 17 beside a system whose list text is 13. Enforced by `scripts/network-reach-audit.sh` (runs in `verify.sh`, static, no build): every host literal in the app must appear EITHER in that registry OR in the audit's explicit non-reach denylist (permalink/display hosts the person's own browser opens on tap, setup doors a connect screen opens, demo placeholders). - RULE (user, 2026-07-08): website icons are ALWAYS inlined as base64 data URIs in `website/index.html` — NEVER hot-link an external `<img src="https://cdn.simpleicons.org/…">` (or any remote image host).
