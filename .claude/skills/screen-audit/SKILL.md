# Screen audit

Recurring sweep that catches regressions between working sessions. Everything runs through `simctl` + launch-arg hooks — **never computer-use** (blocked in scheduled runs).

## Procedure

1. **Build + baseline sweep**: run `scripts/verify.sh`. It builds (correct derivedData path), boots the iPhone 17 Pro sim, installs, runs the **cold-launch survival loop** (10× reinstall + cold launch, each cycle requiring the `launchTimer` first-frame marker — the guard for the intermittent first-frame stack-overflow class that recurred 2026-07-10/13/15; a failure here names the cycle and whether the process died or froze, and is the HIGHEST-severity finding an audit can produce — report it first, with the `launch-survival.log` path), screenshots home/feed/apps, and runs the headless answer probe. If the build fails, first rule out a transient mid-save before calling it the finding: run `git status` — if the working tree has uncommitted edits, the build may have been caught between keystrokes (a half-typed line, e.g. `el.ref` before it becomes `el.str(3)`, reads as a real compile error but isn't). Re-run the build once; if it still fails on an unchanging tree, stop and report the error — THAT is the finding. A failure that clears on rebuild is not a finding — note that it happened and continue against the now-building tree.

2. **Performance pass**: run `scripts/perf.sh`. One headless cold launch captures three metrics — **launch** (init→ready ms, the cold-launch path — a sensitive area per CLAUDE.md's 4MB-stack note), **memory** (steady-state RSS MB, sampled after first frame and before inference), and **answer** (on-device compose ms). It writes `perf.txt` and appends a row to `scripts/output/perf-history.csv` (the rolling baseline). Run it AFTER step 1 — verify.sh's answer probe warms the on-device model, so perf.sh times the *warm* path (a cold first inference is ~10–25s and unrepresentative). The script self-flags regressions vs the previous run (>1.4× launch/memory, >1.6× answer) and absolute ceilings (900ms / 450MB / 12000ms); fold any `⚠` lines from `perf.txt` into the findings as regressions (highest severity, alongside visual regressions). `answer: n/a` means the model was unavailable on the host — environment, not a regression (launch/memory are still captured); note it and move on. The perf numbers are metrics, not screenshots — report the three values every run so trend is visible even when nothing flags.

3. **Extended screen walk.** **First, grant permissions ONCE up front** so no launch trips the iOS 26 Photos dialog: `xcrun simctl privacy booted grant photos com.casberi.app && xcrun simctl privacy booted grant calendar com.casberi.app`. Grant `photos` (full-library read) ONLY — do NOT also grant `photos-add`, and do NOT use `grant all`. The app's foreground cover-photo path requests *full* PHPhotoLibrary access; `grant all` doesn't cover it, and `grant photos-add` sets an **add-only** state that actively provokes the app's "requesting additional access to your Photo Library" upgrade dialog — which then overlays home/Diagnostics/answer/light/Dynamic-Type/onboarding shots (verified 2026-07-11). **Known residual:** even `grant photos` alone may not fully suppress the prompt on iOS 26 — simctl can't pre-grant the exact readWrite tier the app asks for. If the dialog still overlays the home/Diagnostics/answer shots, treat those as environment-obscured, NOT app regressions: the headless answer probe (step 1) is the source of truth for the answer path, Diagnostics runs behind the dialog (its result rows are still partly visible), and a warm re-shot usually clears it. Do NOT report the dialog itself as a finding. **The Photos dialog PERSISTS across app relaunches (verified 2026-07-17) — a reboot clears it, not `simctl erase`.** It is not a per-launch ask but ONE unanswered system alert: once it appears (the `grant photos` residual can trigger it on a plain launch, even after `simctl privacy reset photos`), it sits above EVERY subsequent app terminate+relaunch and silently overlays a whole walk's worth of shots — ~15 in one run. `xcrun simctl shutdown booted` then `boot` + `bootstatus -b` dismisses the stuck alert (far cheaper than the erase the calendar note below reaches for); re-shoot the affected screens after the reboot. Detect it early: if the first extended-walk shot shows the light dialog block mid-screen, reboot before shooting the rest rather than discovering it 15 obscured screens later. **Calendar residual (verified 2026-07-15) — read before touching calendar TCC.** The iOS 26 **"Casberi would like full access to your Calendar"** dialog (with the "49 events in the next year" event preview) is the same class of residual and is the more dangerous one, because it can lock up the *entire* walk. It fires on every app foreground where the `cal` bridge is connected (`BridgeRefresh.swift` gates on `connected("cal")` — the ask is correctly scoped, NOT an app bug), and simctl cannot pre-grant the exact `.fullAccess` tier the app requests (`ScheduleIngest.connectCalendar` → `requestFullAccessToEvents()`). **Do NOT cycle `simctl privacy grant/revoke calendar` or hand-edit `TCC.db` to fight it** — none of those reach the `.fullAccess` state, and worse, they flip calendar from whatever quiet state a fresh install left it in into `notDetermined`, which makes the app re-prompt on *every* launch instead of just some. Once the system calendar daemon (`calaccessd`) has computed the preview once, the dialog appears in <1s on warm relaunches, outrunning even a fast shot, and only a full `simctl erase` resets it (too heavy for a scheduled run, and it resets for just one launch). Practically: verify.sh's baseline home/feed/apps (shot immediately after a cold install, before the daemon warms) are usually the only clean calendar-path shots you'll get; if the dialog has warmed and blocks the extended walk, say so and mark those screens environment-uncovered — do NOT report the dialog, and do NOT burn the run trying to clear it. Then, for each screen below, terminate the app, relaunch with the hook plus `-onboarded YES` (skips first-launch onboarding; omit only when auditing onboarding itself), wait ~7s, `xcrun simctl io <udid> screenshot <name>.png` (the udid from `scripts/sim-device.py`, never `booted`):
   - Settings: `-openSettings YES` (or `-deeplink casberi://settings`). Library has no counts box since prd §1612.
   - Data tray: `-openSettings YES -accountDetail data`. (Diagnostics is deleted, 2026-10-21; the perf readings are `-perfReadingsProbe YES`, logged.)
   - Also grant `microphone` up front, or `-openNote YES -noteVoice YES` raises a mic alert that sticks over every later shot until a reboot (2026-10-20).
   - Sources (the apps catalogue and the counts box): `-deeplink casberi://apps`.
   - Rooms tray: `-openTray YES`; its search: `-openTray YES -traySearch "<words>"`.
   - Rooms: `-openRoom "<seat or category>"` (`Wallet`, `Work`, `Life`, `Your notes` — never "Notes", prd §975), with `-openSection <raw>` for a tile (`home`, `holdings`, `security`, `subscriptions`); `-walletScope <address | seat:Name>`, `-marketsScope alerts|<Category>|new`, `-notesScope folders|voice`.
   - Move tab (prd §1422): `-openRoom "you:move"` (its page; the demo has an account, §1475); `-openMove YES` raises its tray; `-movePreview create|recover|keys` for its other shapes; `-moveSendDraft`, `-moveSwapDraft` for a filled sentence.
   - Search tab: `-openComposer YES` (Find, its field and foot), `-findProbe "<words>"` for a filled result.
   - Note sheet: `-openNote YES` (with `-noteDraft "<text>"`, `-notePicture YES`, `-noteVoice YES` for its other shapes).
   - Contacts (the Contacts app's page, prd §1612): `-openAddresses YES`. What this app reaches: `-openReach YES` (`-seedReceipts YES` for an undeclared host).
   - Thing sheet: `-deeplink casberi://thing/latest` (the newest thing's sheet). Its variants are keyed off the thing's kind (a wallet transfer, a social post); name a variant unreached if the corpus has none of that kind.
   - Person card: `-deeplink "casberi://person/<Bluesky|X>/<handle>"` (Nostr and Farcaster are retired, prd §1109, §1110).
   - Fresh-user onboarding (prd §96/§217): terminate, `xcrun simctl spawn <udid> defaults delete com.casberi.app onboarded`, launch `-fresh YES` with no `-onboarded` arg (`-onboarded NO` masks the greeting's own write). `-fresh YES -howItWorksCTA <s>` fires the cover's button after `<s>` and enters the demo. **Restore after: relaunch `-fresh NO -onboarded YES`**, or every later content shot draws its honest empty state.
   - Empty states: covered by the fresh-user launch above (before restoring the corpus).
   - Account pages are reached from Sources by tapping a row; there is no headless door to one (`-openSetup`, `-openApp`, `-openProject` and `-openPair` are gone). Name the ones you could not reach.
   - The ask is deleted (prd §1047): there is no answer screen to shoot. `-findProbe` and `-openComposer` drive Find, the composer's one deterministic door.
   - Light mode: relaunch each of home/feed/apps with `-theme.light 1` (the app themes from its own AppStorage, NOT the system — `simctl ui booted appearance light` does NOT flip it and yields dark shots mislabelled "light"). Restore by relaunching without the flag (or `-theme.light 0`).
   - Dynamic Type XXL: `xcrun simctl ui booted content_size extra-extra-large`, re-sweep, then restore `medium` (note the underscore in `content_size`). **Broken on the iOS 26.5 runtime (verified 2026-07-20):** the setter and read-back report XXL but nothing rescales — not even the system Settings app, after reboot, in any app. XXL shots there come back pixel-identical to medium; that is the override failing, NOT the app ignoring Dynamic Type (the app's ramp demonstrably scaled on the 26.0 runtime, `scripts/output/20260711-010010/xxl-home.png` vs `home.png`). If an XXL shot looks unscaled, screenshot the system Settings app first — if that's unscaled too, mark the Dynamic Type step environment-uncovered and move on; do NOT file a typography bug or "fix" `Typography.swift`.

4. **Review each screenshot against the law**:
   - `docs/build-brief.md` §8 + CLAUDE.md "Design law" (no hairlines, zero exceptions; the catalog is a sectioned LIST behind a `DSSectionSwitcher` strip and the sources tray is the grid — the two must not share a grammar, §518; no glass on content, tray grammar, no dead controls, no fake status)
   - `docs/prd.md` rulings — flag any screen contradicting a recorded ruling
   - Empty/denied/unavailable states render honestly (no blank panes, no lying copy)

5. **Doc-drift check** — the docs and this skill can fall out of sync with each other and with the app; drift is a finding like any other:
   - CLAUDE.md "Design law" digest vs `docs/prd.md` rulings: read both, flag any rule the PRD has superseded but the digest still states (or vice versa).
   - Walk-list coverage: compare `Casberi/Casberi/Screens/` and the hook list in CLAUDE.md against step 3's walk list — flag any screen or hook the audit never visits.
   - `git log --oneline -5 -- docs/ CLAUDE.md` — if the law changed recently, say so in the report so findings are read against the right version.

6. **Report**: a short findings list ordered by severity — regressions first, then honesty violations, then polish. Always include the perf pass's three numbers (launch / memory / answer) so the trend is on the record even when nothing flags. Each finding names the screenshot file and the doc/ruling it violates. No findings = say so plainly. Do NOT fix anything during an audit run unless asked; findings go to the user (or the session report) for triage.

7. **File the findings as issues** (`scripts/file-findings.py`, 2026-10-14). Every regression, honesty violation and polish finding from step 6 becomes one GitHub issue labelled `claude` and `source:screen-audit`, so the next working session picks it up without being told. Environment-obscured screens, WIP-in-flight screens and perf numbers that did not flag are NOT findings and are not filed.
   - **Reuse keys first.** Run `scripts/file-findings.py --list --source screen-audit`. It prints each open issue as `#N  key  title`. A finding that is the same defect as an open issue takes THAT key exactly — a key is the identity, and a new spelling files a duplicate. A new finding gets a key `<screen>-<defect>` in lowercase words joined by `-` (`settings-tray-hairline`, `home-lede-clipped`).
   - **Write `scripts/output/<ts>/findings.json`:** `{"source": "screen-audit", "findings": [{"key", "title", "body"}], "resolved": [keys]}`. The title is the defect in one sentence. The body names the screenshot file (relative to the repo), the ruling or doc line it breaks (`prd §N`, `build-brief.md §8`), and the hook that reproduces it. `resolved` lists each open key whose screen you shot clean this run. A key whose screen you did not reach stays out of both lists.
   - **Never set `"complete": true`** — a screen-audit's keys are chosen per run, so closing by absence would close what a run merely spelled differently. Close only through `resolved`.
   - Run `scripts/file-findings.py --json scripts/output/<ts>/findings.json` and put its `findings:` line in the report. The repo is PUBLIC: no screenshot is attached, no corpus content (titles of things, names, addresses, amounts) is quoted — describe the defect, not the data. The filer withholds a credential-shaped field; it cannot see a person's data.

## Notes

- Screenshots land in `scripts/output/<timestamp>/` (gitignored).
- The sim inherits the host Mac's Apple Intelligence state — "model unavailable" on a fresh host is environment, not regression.
- Schema changes wipe the sim install (theme resets to Blue/dark, demo corpus reseeds) — note it in the report so theme drift isn't misread as a bug. Corpus counts (things per week, feed totals, rows in an answer) therefore differ run-to-run — never a regression on their own.
- **Moving-target guard.** Run `git status` before building. If the tree has uncommitted WIP touching screens you're about to audit (Home especially — `HomeScreen`/`HomeComposition`/`GenUI`), that screen may render half-built (missing titles, new hint strings, restyled widgets). Mark such screens WIP-in-flight and NOT-a-regression in the report, and re-audit once the work lands — do not file WIP as a bug. The tree can also change *under* the run (a file you built compiles differently minutes later); if a shot looks wrong, re-read the live source before writing it up.
- **Launch args are STICKY — they are UserDefaults, not argv.** Every `-flag value` a launch passes is *written* to the app's defaults and survives into the NEXT launch that doesn't overwrite it. This silently poisons a walk: `-openSetup "Apple Notes"` from shot 6 was still set at shot 9, so a `-openProject` launch opened the "Your key" tray instead; a stale `-onboarded YES` defeated `-fresh YES` and produced a *blank Home* that reads exactly like an empty-state bug but is the audit's own residue (verified 2026-07-16). Clear the ones you're done with before the next shot — `xcrun simctl spawn booted defaults delete com.casberi.app <key>` (`openSettings`, `accountDetail`, `openRoom`, `openSection`, `openTray`, `openNote`, `openAddresses`, `openReach`, `settingsScope`, `deeplink`, `theme.light`, `onboarded`) — or uninstall+reinstall for a genuinely clean state (that also wipes the corpus and reseeds). If a shot shows a screen you didn't ask for, suspect the previous shot's args before you write it up.
- **Cold-load skeletons are timing, not bugs.** Home's pinned/thread widgets stream in — a ~4s shot can catch them as skeleton rows before content resolves. Confirm by re-shooting (or check a later warm shot, e.g. the Dynamic-Type re-sweep, where the same widget shows real rows) before reporting an "empty" widget.
- **Stale in-app language ≠ localization bug.** The app has its own language switcher (`app.language` in its UserDefaults, separate from the device's `AppleLanguages`), which can be left on a non-English value by a prior session — so early shots (e.g. the verify.sh home) may render in Spanish while later shots are English, because a `-fresh`/reinstall mid-walk reset `app.language` back to `en`. Before reporting a "localization inconsistency," check `xcrun simctl spawn booted defaults read com.casberi.app app.language`; if it's not `en`, that's the cause — normalize (re-shoot at `en`) rather than filing a false finding. Sample content (project names like "Work") stays English by rule even when the UI is localized — not a gap.
- **Perf numbers are noisy — trend over single runs.** `perf.sh` flags a metric only when it beats a ceiling or is >1.4–1.6× the *previous* run, so one-off spikes self-limit, but a truly cold run (model not pre-warmed, or a schema-wipe reseed changing the corpus the answer path walks) can move `answer` a lot without any real regression. Read the flag against `perf-history.csv`: a single outlier that snaps back next run is host jitter, not a code regression. `launch` (init→ready = the app's own render path, corpus-independent) and `memory` are the steadier signals. `answer: n/a` = model off on the host, benign. The perf pass depends on step 1 having already warmed the model — if you skip step 1 and run `perf.sh` standalone, the first inference is cold and `answer` will read high (or time out to n/a).
